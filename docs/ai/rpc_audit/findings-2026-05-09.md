# RPC Traffic Audit — Session 2026-05-09

Findings from the first capture session of the audit defined in
`docs/issues/1581-rpc-traffic-audit.md`. The app talked to the local
seeded server (confirmed: persistent TCP between server pid and the
iOS Simulator's `Runner` process). All server-log analysis below is
filtered to the post-seed window (after 09:05:30, when the simulation
finished).

Findings are ranked by impact-to-fix ratio. Each row should become its
own GitHub issue once we agree on scope.

## F0 — `request_id` correlation between client and server is broken [HIGH, instrumentation]

This is the most consequential finding from the session because it
breaks the audit join key.

- The Flutter client emits 619 `RPC_AUDIT` lines, each with a unique
  UUID generated in `RpcUtils.buildHeaders()` and stamped into the
  `X-Request-ID` header.
- Server-side, the post-seed window contains exactly **127** distinct
  request_ids, **none of which match any client request_id**. Sampled
  20 client request_ids → 0 server hits each. Sampled 10 server
  request_ids → 0 client hits each.
- Of those 127 server request_ids, **one** (`748b9982-…`) appears
  **3,424 times** spanning unrelated RPCs (login, ListCommunities,
  StreamCommunityEvents, multiple StreamMessages instances spanning
  several conversations, social context resolution, etc.). The other
  126 are mostly each used once, attached to a `/media/` GET (which
  doesn't carry the X-Request-ID header at all, so the middleware
  generates one).

There are two distinct bugs collapsing here:

1. **The Connect Dart transport seems to be sending one
   `X-Request-ID` for the entire HTTP/2 connection's lifetime,**
   not one per RPC. `buildHeaders()` is called per call and generates
   a fresh UUID, but only the first one reaches the server, and even
   that one is unrecognizable to the client because `RPC_AUDIT` lines
   show very different IDs.
2. **The server's request-id middleware appears to read X-Request-ID
   once per HTTP/2 connection** (or once for the first multiplexed
   request) and reuses that ID for every internal log line on every
   subsequent RPC and every long-lived stream goroutine — see the
   3,424 count.

Either bug alone would make correlation hard. Both together make it
impossible.

**Action:** investigate Connect-Dart header behavior on HTTP/2; verify
the server middleware is registered per-request (per
`http.HandlerFunc`) and not at a higher level. Until correlation is
fixed, every other finding in this audit is harder to chase: we can
see counts on each side but can't join them. Filed as a blocker for
the next pass.

## F1 — Streams reconnect on a 2-minute cycle for the entire session [HIGH]

```
24 stream-started events (StreamCommunityEvents + StreamMessages)
20 stream-ended events
   reason=context_done context_error=context canceled
12 streams ended at duration_ms=120000
 4 streams ended at duration_ms=120001
 3 streams ended at duration_ms=119999
 1 stream ended at duration_ms=119998
```

Every single ended stream hit ~120 s. That's a fixed timeout
somewhere — either the server enforcing a 2-minute idle deadline, or
the Connect-Dart client cancelling. Across a 7-minute walkthrough that
means each stream cycle is roughly: connect → idle for 2 min →
context cancelled → reconnect. With ~6 conversations open, you can
get a `StreamMessages` reconnect every ~20 s on average.

Each reconnect is a fresh server-side stream registration
(`registered event stream community_id=…`), a fresh goroutine, fresh
DB query for initial state, and `auth` middleware reruns (see F2).

**Action:** find the 2-minute timeout. Likely candidates:
- A `context.WithTimeout(120s)` somewhere in the Connect transport.
- Cloud-Run-style request-deadline being inherited locally.
- A keepalive/idle-timeout on the server's HTTP/2 server.

Whichever it is, raise it to "session lifetime" or implement a server
keepalive that the client recognizes so existing streams stay open.

672 token validations over 127 HTTP requests is ~5× per request. Looks

**Action:** verify auth runs once per HTTP request via middleware and
the result is stored in context; remove redundant `ValidateToken`
calls from individual handlers / services. Out-of-scope for the
client audit but visible from this data.

## F3 — Chat-message-count polling [MED]

`GetConversationMessageCount` ran **67 times** in 7 minutes. With
~6 active conversations that's ~10 polls per conversation per session,
or one every ~40 s per conversation. Plausibly correct for unread
badge updates, but also potentially redundant given there are 13
active `StreamMessages` connections that already deliver new-message
events.

**Action:** check whether the inbox / chat list is polling counts
even while a `StreamMessages` connection is open for the same
conversation. If yes, drop the polling for streamed conversations and
let the stream be the source of truth.

## F4 — Media URL cache thrash inside one session [HIGH]

For a 7-minute session looking at one community, the
`MediaRepository` cache **misses on the same `mediaId` up to 14
times**.

| mediaId (truncated) | misses | hits |
|---|---|---|
| `media:07cd6133-…` | 14 | 0 |
| `media:e816f9dd-…` | 13 | 11 |
| `media:34ecbf3d-…` | 13 | 0 |
| `media:1bafdf4a-…` | 13 | 25 |
| `media:7c96fec3-…` | 12 | 0 |
| `media:35f679e0-…` |  6 | 0 |
| 16 other media keys | 4 | varies |

For the heaviest thrasher (`1bafdf4a`), the timeline alternates
miss→hits→miss→hits over ~5 minutes:
```
09:19:00.441  miss
09:19:00.465  hit
09:19:00.466  hit
09:19:00.601  hit
09:19:00.602  hit
09:19:50.278  miss   ← 50 s later, with 30-min TTL configured
09:19:50.392  hit
09:20:22.111  hit
09:20:29.687  miss
09:20:29.688  miss   ← stampede (see F5)
09:21:47.660  miss
09:23:04.931  miss
09:23:42.063  hit  …
```

`MediaRepository.getMediaUrl()` is the canonical example of a value
that should be sticky for the life of a session — `mediaId` is
stable, the cache is namespaced and TTL'd at 30 minutes, and the
mediaId-derived `cacheKey` is what `CachedNetworkImage` uses on disk.
Refetching the metadata 13 times means 13 hits on
`MediaService.GetMedia`, each doing a DB lookup and presigning a URL.

Hypotheses:
1. Some screen invalidates media keys on viewmodel rebuild.
2. `AccessedExpiryPolicy` is misconfigured (e.g. 30 *seconds* instead
   of 30 *minutes*).
3. Different code paths hold different `MediaRepository` instances
   each with its own private cache (provider scoping issue).

**Action:** instrument `MediaRepository` with a per-instance
identifier and include it in `CACHE_AUDIT` to test (3); add a
regression test asserting that two `getMediaUrl()` calls for the
same id within the TTL hit the service exactly once.

## F5 — Cache stampede: simultaneous misses for the same key [HIGH]

```
09:20:29.687  CACHE_AUDIT key=media:1bafdf4a-…  result=miss
09:20:29.688  CACHE_AUDIT key=media:1bafdf4a-…  result=miss
```

Two `MediaRepository.get` calls 1 ms apart, both miss, both fetch.
Without dedup the server gets two parallel `GetMedia` calls for the
same id. Several other media keys exhibit the same pattern.

`CacheManager.get` is documented as "fetch on miss"; the in-flight
fetch for the first caller is not joined onto by the second. With N
simultaneous renders of the same item this is N × the work.

**Action:** single-flight inside `CacheManager.get` — first miss takes
the lock, subsequent callers `await` the same `Future`. Add a unit
test that fires 5 parallel `get()` calls and asserts `fetch` ran once.

## F9 — Audit instrumentation gaps [MED, instrumentation]

Two gaps surfaced by this run:

1. **`operationName` is unset for almost every client RPC.** Of 619
   `RPC_AUDIT` lines, only `RecordAttendance` has a real name; the
   other 618 say `rpc=unknown`. Every service method in
   `app/lib/services/*.dart` should pass `operationName:` to
   `RpcUtils.executeRpc`.
2. **Screen attribution falls through to widget runtime types.** Of
   619 RPCs, 312 (50%) are `screen=unknown` (fired pre-route),
   232 (38%) are `screen=Builder<dynamic>` (GoRouter routes don't
   set `settings.name`). The remaining 12% are
   `Dialog<…>`/`ModalBottomSheet<…>`. None resolves to a
   human-readable screen name. Fix in `_extractScreenName` to consume
   GoRoute's `name` field, or set `RouteSettings(name: …)` on every
   `GoRoute` definition.

Without (1) we can't group client logs by RPC method without a
server-side join. Without (2) we can't attribute bursts to specific
screens.

## F10 — Middleware close-line missing for `/ripls.api/*` [LOW, instrumentation]

The server's logging middleware emits the per-request close line
(`http request method=POST path=/ripls.api…`) for the seeding phase
(11,717 such lines) but emits exactly **zero** during the post-seed
walkthrough. Only `/media/...` GETs produced close lines (119 of
them). Yet inner-function debug logs prove unary RPCs ran (login,
ListCommunities, GetUserByID, GetPortfolioInboxFeed, search, …).

Two scenarios:
- HTTP/2 multiplexing routes those Connect calls through a path that
  bypasses the standard `http.Handler` middleware chain.
- The middleware writes the close line into a different log sink that
  isn't captured in the file we tee'd.

Either way it means we lost `db_queries`/`response_bytes` per RPC
during the walkthrough. The seeding phase used HTTP/1 (Go sim binary)
and middleware worked; the app uses HTTP/2 and it didn't.

**Action:** confirm the middleware is wired into the same handler
chain that Connect's HTTP/2 path goes through. This is likely the
same root cause as F0; might collapse to one fix.
