# Issue #1249: Defer experience/request impact metrics until completion; derive via LLM with user override

**Source:** https://github.com/Type2Fun-Foundation/ripls/issues/1249
**Filed:** 2026-04-23 | **Last activity:** 2026-04-23
**Labels:** enhancement | **Assignees:** unassigned
**Context docs:** [docs/impact_metrics/aggregate.md](../impact_metrics/aggregate.md), [docs/impact_metrics/money_saved.md](../impact_metrics/money_saved.md), [docs/impact_metrics/emissions_prevented.md](../impact_metrics/emissions_prevented.md), [docs/impact_metrics/quality_time.md](../impact_metrics/quality_time.md), [docs/impact_metrics/time_saved.md](../impact_metrics/time_saved.md)

## Problem Statement

For experiences and requests, today's impact metric display has two problems:

1. **Premature display.** SAVED / CO2 AVOIDED / QUALITY TIME tiles render throughout the lifecycle using flat per-type defaults (e.g. experience CO2 = 0 g, request CO2 = 5,000 g flat, QT duration = 120 min flat, vulnerability via type lookup). Pre-completion, these are mostly noise — and showing zeros reads as "this had no impact" rather than "we don't know yet."
2. **Coarse estimation.** The estimator inputs are dominated by transaction-type lookups, ignoring the rich data we now have at completion: title, description, chat transcript, location, scheduled time, confirmed attendee list, and structured needs/contributions ([PlanningNeed](../../proto/ripls/models/planning.proto), [PlanningContribution](../../proto/ripls/models/planning.proto)).

The ask is twofold: (a) hide impact tiles for experiences and requests until the user reaches the completion modal, and (b) at completion, run an LLM-assisted enrichment pass over the rich context to draft per-attribute values, with each tile tappable to a detail modal that lets the user override individual inputs. Final values persist with provenance distinguishing LLM-drafted vs user-overridden so calibration and refresh-gating keep working.

Gear behavior (loans, giveaways) is explicitly unchanged in this issue.

This issue consolidates three existing Future Work sections in [aggregate.md](../impact_metrics/aggregate.md): "LLM-Assisted Request/Experience Estimation", "Refine Estimates at Transaction Completion", and "LLM-Assisted Quality Time Enrichment".

## Potential Solutions

### Option A: New `DraftImpactEstimate` RPC + per-input provenance schema across all three metrics
- **Approach:** Add a dedicated read-only RPC that runs the same enrichment + builder flow as completion but doesn't persist. Extend `QualityTimeAttributes`, `MoneySavings`, and `PreventedEmissions` so each *input* field carries its own value + `Provenance`. The composite/final values (`money_saved.value_usd`, `manufacture_avoided_carbon`, `quality_time_minutes`) remain computed-only, never user-overridable. Completion modal calls `DraftImpactEstimate`, renders three tappable tiles, opens detail modals where the user edits inputs only. Final commit goes through the existing completion RPC, passing user-overridden inputs.
- **Pros:** Clean separation between draft and commit. Per-input provenance unlocks the audit-trail UX the docs already imagine but never wired up. `ShouldRefresh()` keeps working naturally — user-overridden inputs have `source=USER` and are skipped on backfill. The "composite is never user-set" invariant is enforced by the schema itself: the user has no way to write a composite directly.
- **Cons:** Schema change touches `QualityTimeAttributes`, `MoneySavings`, and `PreventedEmissions` — propagates through builder, storage, and any client code that reads these messages. New RPC adds API surface area.
- **Effort:** Large. Schema work + new RPC + completion modal refactor + detail modals + display gating.

### Option B: Extend completion RPC with dry-run mode + composite-level provenance only
- **Approach:** Add a `dry_run` flag to existing completion RPCs (`CompleteTransfer`, `MarkRequestFulfilled`, `CompleteExperience`). When true, server runs the enrichment, returns the impact, but doesn't transition state. Don't add per-attribute provenance — just stash overridden raw values in `QualityTimeAttributes` and rely on the composite `Provenance.source = USER` to mark the whole estimate as user-edited.
- **Pros:** No new RPC, no schema change. Smallest surgical footprint.
- **Cons:** Composite-level provenance loses fidelity — if a user only overrides one attribute (e.g. group size from 8 → 6), we lose the signal that the LLM-drafted vulnerability was correct. `ShouldRefresh()` then either sticks with all stale values forever or refreshes everything (clobbering the one override). Also overloads the completion RPC, which already handles state transition + impact + community event + story generation — adding a dry-run branch makes it heavier.
- **Effort:** Medium. Cheaper now, more expensive later when calibration needs per-attribute granularity.

### Option C: Client-only display gating + reuse current completion-time impact
- **Approach:** Hide impact tiles pre-completion but otherwise leave the system alone. The completion lifecycle already calls `aiProvider.InferSocialAttributes()` and persists impact. Display the result post-completion as we do today; don't add the override UX.
- **Pros:** Smallest possible change. Ships the user-visible problem (premature/wrong-looking metrics) without any backend work.
- **Cons:** Drops the override UX entirely, which is half the issue. Doesn't enrich the estimation logic. Doesn't address the coarse-defaults problem at all.
- **Effort:** Small. But it punts on the core ask.

## Recommendation

**Option A**, phased. The per-input provenance schema is the only change that makes the override UX truthful — without it, "user overrode group size but kept the LLM vulnerability" becomes indistinguishable from "user accepted everything," and calibration data is corrupted from day one. The new `DraftImpactEstimate` RPC is also the cleaner separation; the completion RPCs are already large and adding a dry-run branch makes them harder to reason about.

Per the Decisions section, the per-input provenance applies to all three metrics — QT attributes plus money inputs (per-contribution value, hire-equivalent rate, etc.) plus CO2 inputs (per-contribution embodied carbon, weight, travel-avoided distance, etc.). The composite values are computed-only and never directly settable by the user.

Option B is tempting for speed but the corner we'd be cutting (composite-only provenance) is exactly the corner that breaks future work. Option C is too narrow to call this issue done.

I'm recommending Option A even though it's the largest because the schema change is one-time and unblocks both this issue and the existing-but-stubbed audit trail / suggest-correction UX referenced in [aggregate.md](../impact_metrics/aggregate.md).

## Decisions

The open questions raised during planning have been resolved as follows:

- **Per-attribute provenance scope** — **Decision: extend to money/CO2 input fields too, not just `QualityTimeAttributes`.** Each input that flows into a metric (e.g. estimated item value, material classification, embodied carbon, travel-avoided distance, hire-equivalent rate, per-contribution value) needs its own value + `Provenance` so the user can override individual inputs. **The final composite values (`money_saved.value_usd`, `manufacture_avoided_carbon`, `quality_time_minutes`) are NEVER user-overridable** — they are always deterministically derived from the inputs by the Go estimator. This is a strict invariant: the override UX must only mutate inputs, never the composite. See Phase 1 for the schema implications.
- **Should the new draft+override UX extend to gear loans/giveaways for consistency?** — **Decision: No, not in this issue.** Once the experience/request flow ships and stabilizes, file a separate follow-up GitHub issue to bring loans/giveaways into the override UX. Until then, loans/giveaways keep their current single-LLM-call-at-completion behavior. (Action item: file the follow-up issue *after* Phase 2 of this issue ships, not before.)
- **What gates pre-completion hiding — transaction state, or absence of stored `ImpactEstimate`?** — **Decision: transaction state.** Hide tiles when state is not in {COMPLETED, FULFILLED} for experiences/requests respectively. State-based gating is robust against the case where impact is computed early (e.g. a draft is fetched but not committed).
- **How big a chat transcript do we send to the LLM?** — **Decision: cap at the most recent 50 messages or a 4,000-token budget, whichever is smaller.** Document the caps in `config.textproto` as `experience_chat_transcript_max_messages` and `experience_chat_transcript_max_tokens`. Revisit if production data shows experiences/requests with significantly longer threads.
- **Attendee privacy in the LLM prompt** — **Decision: pass attendee user IDs and aggregate counts only — never display names or emails.** If we later want richer signals (e.g. "host has high tie strength to most attendees"), pass anonymized graph features (counts, tie-strength tiers) rather than identities.
- **Where does the new RPC live?** — **Decision: on the existing impact metrics service** ([server/services/impact_metrics/](../../server/services/impact_metrics/)), in a new file `drafting.go` (per the audit-noted file-size discipline). Don't add it to transfer/request/experience services — those are state-machine services and the draft is read-only.
- **Backfill: re-run on historical completed experiences/requests, or only forward?** — **Decision: forward-only on first ship.** Existing stored impacts have composite-level `Provenance` with the old algorithm version; `ShouldRefresh()` will pick them up automatically when the version bumps, via the existing backfill job — no special migration needed for this issue. Calibration data accumulates from new completions.
- **Should the override detail modal recompute the composite client-side or call the server?** — **Decision: server-side via a redraft of the same RPC with overridden inputs.** Keeps the formula in one place (the Go estimator), avoids drifting Dart/Go math, and reinforces the "composite is never user-set" invariant — the server is the only thing that ever produces a composite.

## Audit Notes

The following items were added or modified during architectural review against [docs/client/architecture.md](../client/architecture.md), [docs/client/caching.md](../client/caching.md), [docs/client/i18n.md](../client/i18n.md), and [docs/server/architecture.md](../server/architecture.md):

1. **Server-side service independence** — The new `DraftImpactEstimate` RPC must access chat messages, planning needs/contributions, and the experience/request record itself. Per [server/architecture.md "Service Independence"](../server/architecture.md), services must not depend on other services. Access these via `storage.ProtoSQLStorage` directly (`QueryByField`, `GetByID`), not by injecting `chat.Service` / `experience.Service` / etc. This matches the existing impact metrics pattern. Added explicit task to Phase 1.
2. **File organization for impact_metrics service** — [server/services/impact_metrics/service.go](../../server/services/impact_metrics/service.go) is already substantial. Per [server/architecture.md "Short, Focused Files"](../server/architecture.md) (< 500 lines target, < 1000 max), the new draft logic goes in a new file `server/services/impact_metrics/drafting.go` rather than appending to `service.go`. Authorization helpers go in `authorization.go` if needed. Added to Phase 1.
3. **Server authorization** — The plan didn't specify who can call `DraftImpactEstimate`. Added: caller must be the experience host or a confirmed attendee (for experiences), or the request creator or a confirmed helper (for requests). Use `auth.UserFromContext(ctx)` and return `connect.CodePermissionDenied` otherwise. Added to Phase 1.
4. **Structured logging** — Per [CLAUDE.md](../../CLAUDE.md) and [server/architecture.md "Observability"](../server/architecture.md), the new RPC handler must use `logging.LoggerWithContext(ctx)` with operation name and entity IDs; never `log.Printf` / `fmt.Printf`. Mask any user data (`logging.MaskEmail`). Added to Phase 1.
5. **Client repository: draft results are NOT cached** — Drafts depend on freshly-pulled chat/contributions/attendee data, and the LLM call should reflect the current state when the user opens the modal. The new `draftImpact()` / `redraftImpact()` methods on [impact_metrics_repository.dart](../../app/lib/data/repositories/impact_metrics_repository.dart) bypass `CacheService.get()` and call the service directly. They still live on the repository (per [client/architecture.md "Repositories are the ONLY layer that calls Services"](../client/architecture.md)) — they just don't cache. Documented in Phase 2.
6. **Cache invalidation after completion** — When the user finally commits via `CompleteExperience` / `MarkRequestFulfilled`, the impact metrics aggregations (community-level, user-level) become stale. Per [client/caching.md "Pattern 2"](../client/caching.md) and "Pattern 7", the existing `ImpactMetricsRepository.invalidate*()` and `dailyCacheInvalidationProvider.notify()` paths must be triggered. `ExperienceRepository` and `RequestRepository` already notify `dailyCacheInvalidationProvider` after completion mutations — verify and extend if needed. Added to Phase 2.
7. **Cache key naming for any new keys** — If any draft state needs short-lived caching (e.g. caching the *initial* draft so that opening a tile detail and returning to the modal doesn't re-trigger the LLM), use the namespace `'impact_draft'` with key `'experience:{id}'` or `'request:{id}'` per [client/caching.md "Cache Key Naming Convention"](../client/caching.md). Cleared on completion or after 5 minutes. Added as an open implementation choice in Phase 2.
8. **Riverpod / Freezed / async safety patterns for new ViewModels** — The completion-modal logic and per-metric detail modals need state management. Per [client/architecture.md](../client/architecture.md): use Freezed state classes (with `@freezed` annotation and `copyWith`), Notifier or AsyncNotifier (prefer AsyncNotifier when the state is fundamentally an async load), `NotifierProvider.autoDispose` for screen-scoped state, `if (!ref.mounted) return;` after every async gap, and disposal tests in `app/test/presentation/viewmodels/`. Added to Phase 2.
9. **i18n: every new string in both ARB files** — Per [client/i18n.md](../client/i18n.md), every user-visible string in the new modals (tile labels, attribute editor labels, error messages, "Override" / "Reset to suggestion" buttons, etc.) must be added to both [app/lib/l10n/app_en.arb](../../app/lib/l10n/app_en.arb) and [app/lib/l10n/app_es.arb](../../app/lib/l10n/app_es.arb) with the `impact*` or `metricDetail*` prefix. ViewModels return enums/codes; widgets resolve via `context.l10n.*`. CI will fail otherwise (`npm run lint:dart:i18n`). Added to Phase 2.
10. **Theme-aware colors only** — The new modals must use `AppColors.xxx(context)` for backgrounds, borders, text — never `Colors.white`, `Colors.grey[50]`, hardcoded hex, or `Color(0xFF...)`. The existing impact widgets (`audit_trail_step.dart`, `comparison_card.dart`) use this convention; copying them brings the right pattern. Added to Phase 2.
11. **Modal vs full-screen navigation** — The per-metric detail "modals" should be implemented with `showModalBottomSheet()` (a [client/architecture.md "Widget Async Exception"](../client/architecture.md#widget-async-exceptions)) rather than `NavigationHelpers.pushScreen()`. Bottom-sheet modals don't need `SwipeToCloseMixin`. Use `if (!mounted) return;` between any awaited modal result and a follow-up navigation call. Added to Phase 2.
12. **Disposal tests** — Per [client/architecture.md "Disposal Testing"](../client/architecture.md): all async Notifiers must have a test that starts an async op, disposes the container, and asserts no throw. Added to Phase 2 testing tasks.
13. **Build verification** — Per [CLAUDE.md "Go Server Build Verification"](../../CLAUDE.md), every Go change must pass `npm run build` (golangci-lint with `gofumpt`, `godot`, `revive` plus `go build ./...`). Added to each server-touching phase.

**Goal:** Backend can produce a complete LLM-enriched draft for any in-flight experience or request, returning per-attribute provenance, without touching client UX.

**Phase 5 Architectural Audit Notes:**

The following items came out of audit against [client/architecture.md](../client/architecture.md), [client/caching.md](../client/caching.md), [client/i18n.md](../client/i18n.md), and [server/architecture.md](../server/architecture.md) — additional to the phase-1/2 audit notes above:

A. **Debounce timer lifecycle.** The 250ms toggle debouncer is a `Timer` held by the notifier. Per [client/architecture.md "Resource Cleanup"](../client/architecture.md) and "Manual Stream Management", cancel it in `ref.onDispose(() => _timer?.cancel())`. Also cancel on every toggle before scheduling a new one (otherwise rapid taps stack timers). Disposal test required.

B. **`ref.mounted` after debounce.** The debounced callback fires on a `Timer`, not inline. By the time it fires, the notifier may have been disposed (user dismissed the modal during the debounce window). Guard the callback body with `if (!ref.mounted) return;` **before** the `await redraftImpact(...)` and again **after** it before the `state = ...` write. This is the same pattern as [client/architecture.md "Async Safety in Notifiers"](../client/architecture.md#async-safety-in-notifiers) but applied to timer callbacks. Consider migrating to `AsyncNotifier` to simplify.

C. **Redraft bypasses the cache.** Live-redraft-on-toggle must NOT hit `CacheService.get()` — the whole point is that the total animates with each toggle, so returning a stale cached composite defeats the purpose. Use the existing pattern from Audit Note #5 (phase-1/2 notes): `ImpactMetricsRepository.redraftImpact()` calls the service directly and returns. It still lives on the repository per [client/architecture.md "Repositories are the ONLY layer that calls Services"](../client/architecture.md) — it just doesn't wrap in `_cache.get(...)`.

D. **No cascade invalidation from toggle redrafts.** The pre-completion redraft does **not** mutate server state, so do **not** call `dailyCacheInvalidationProvider.notify()` or `invalidate*()` from the toggle path — that would nuke unrelated caches on every tap. Cache invalidation only happens on the final `CompleteExperience` / `MarkRequestFulfilled` commit, which Phase 2 already wires up.

E. **TabController is a Flutter widget resource, not Riverpod state.** The `TabController` lives on a `StatefulWidget` with `SingleTickerProviderStateMixin`, initialized in `initState()` and disposed in `dispose()`. Do not try to hold it in a Notifier. This is how [loan_manage_modal.dart](../../app/lib/presentation/screens/gear/loan_manage_modal.dart) does it and matches [client/architecture.md "No Controllers"](../client/architecture.md) — the controller here is a Flutter SDK class (`TabController`), not a custom "controller" pattern.

F. **Recovered Details-tab row widgets go through l10n + theming before landing.** The input-row widgets ported from the gear / experience / request Details tabs (SHAs `73e3349e` for gear; locate equivalents for experience and request via `git log --diff-filter=D --follow`) pre-date the current theming and i18n conventions — they carried hardcoded English strings and `Color(0xFF...)` values. Per [client/i18n.md](../client/i18n.md) every user-visible string must live in ARB files (`impact*` / `metricDetail*` prefix), and per [client/architecture.md "Colors and Theming"](../client/architecture.md) every color must resolve through `AppColors.xxx(context)`. Scrub both before re-committing; `npm run lint:dart:i18n` + widget inspection catch misses.

G. **Composite-is-computed invariant in the UI.** Phase 1 enforces this at the proto/RPC layer (composite rejected in the override path). The UI must reinforce it: no editable widget should be bound to the composite field. The shared "composite at the top" layout uses `Text`/`Container`, never `TextFormField`. This matters because removing the edit icon (task 2) removes the *hint* of editability but doesn't remove the *capability* — so the widget type itself must exclude it.

H. **Phase 5 is client-only.** No server changes are required — `DraftImpactEstimate` and its with-overrides variant already exist from Phase 1, and the live-toggle redraft consumes the same RPC. No new protos, no new RPCs, no `npm run build` for Go. This does mean Phase 5 assumes redraft P50 latency is already low (sub-200ms) — verify on the existing RPC before starting, since the UX feel depends on it.

I. **Service independence doesn't apply here.** No new server services. The only server-side consideration: if the redraft RPC's latency degrades, examine its storage access (`QueryByField` / `GetByID` for chat messages, contributions, RSVPs) rather than injecting another service — per [server/architecture.md "Service Independence"](../server/architecture.md) and existing Audit Note #1.

J. **No cache key changes.** Phase 5 doesn't introduce any new cached entries. Audit Note #7 (optional `'impact_draft'` cache) remains an option not taken. Stick with no-cache for drafts/redrafts so the live total stays truthful.

K. **Disposal tests are mandatory, not optional.** Per [client/architecture.md "Disposal Testing"](../client/architecture.md): the new `TabController`, the debounce `Timer`, and any notifier holding a future all need disposal tests. This is separate from the widget tests — the disposal test starts an async op, disposes the container, and asserts no throw.

**Phase 6 audit notes:**

- **One canonical layer per invariant.** Don't re-assert an invariant everywhere it happens to be visible — that produces a brittle test matrix. If a test fails in a non-canonical layer, raise the primary layer first and delete the incidental assertion.
- **No LLM-quality tests in the suite.** Do not pin specific LLM outputs (the model changes; tests break; people disable them). LLM quality belongs in the Phase 4 calibration dashboard + an off-CI nightly golden-set eval (follow-up, not this phase). See [testing.md §6](../cowork/tmp/testing.md).
- **Fake AI provider, not the real client.** Every server test path that touches `aiProvider.InferSocialAttributes` uses a fake. This keeps the default suite deterministic and hermetic; reserve `//go:build integration` for cases that genuinely require a live external call.
- **Widget tests wrap `MaterialApp` with l10n delegates.** Every widget test under this phase imports `app/test/helpers/l10n_helpers.dart` and uses its wrapper. A missing wrapper surfaces as "no MaterialLocalizations found" at runtime per [client/i18n.md](../client/i18n.md).
- **Mocks never hit a real service.** ViewModel and repository tests use `ProviderContainer` + Mockito mocks per [client/caching.md "Testing"](../client/caching.md).
- **Keep [testing.md §9 "Keeping this doc honest"](../cowork/tmp/testing.md) current.** When a new metric, invariant, or layer is added, update §2.1, §3, and §4 in the same PR — the test file and the plan file co-evolve.
