# Issue #1367: Feed feels slow loading experiences (waiting to load videos?)

**Source:** https://github.com/Type2Fun-Foundation/ripls/issues/1367
**Filed:** 2026-04-25 | **Last activity:** 2026-04-27
**Labels:** none | **Assignees:** unassigned
**Context docs:** none

## Problem Statement

When a user swipes vertically in the home feed, each new experience page renders a black screen with a centered spinner for several seconds before any content appears. The block matches the time required to download the experience's full background video and call `VideoPlayerController.initialize()`. Title, description, time, location, RSVP buttons, chat, etc. — all of which are already known after a fast metadata fetch — are withheld behind the same `isLoading` gate as the video. The result: the feed feels sluggish even though most of the content is ready almost immediately.

The reviewer (`maintainer`) clarified the desired behavior: "Better would be to immediately show all the textual content and then start the video once it's there." A follow-up comment refined the static-while-loading frame: "If it's possible to just show the first frame of the video quickly without loading the whole thing, that's a desirable enhancement: first show textual info, show first frame as static, then start video when its loaded." The reviewer also expanded the scope: the same pattern should apply to **all item detail screens** (gear, request, community, story), not just the experience screen.

That is: decouple text from video so the perceived load time of any feed item drops from "video download time" to "metadata fetch time" (~100ms), and bridge the gap to autoplay with a static first frame already cached on the client.

**On "first frame":** the server-generated thumbnail produced by #847 is, by design, a frame extracted from the source video — it *is* the static first-frame image the reviewer is asking for. We don't need a separate client-side first-frame extraction (which would require downloading enough of the video to decode a frame and would defeat the point). Reusing `MediaItemData.thumbnailUrl` gives "first frame as static" for free, with no extra round-trip; the only client cost is rendering the JPEG that's already in `state.allMediaItems[0].thumbnailUrl`.

## Context from Comments

The author files the bug, suspects the cause is "blocked waiting for the whole video to come down," then a maintainer comment narrows the desired fix: textual content first, video starts once available. A follow-up review on the plan PR (#1473) added two refinements that this revision incorporates: (1) explicitly call out "first frame as static" while the video loads — already provided for free by the existing #847 server-generated thumbnail, and (2) apply the pattern to *all* item detail screens in this PR, not only experiences. Cross-page video preloading is still out of scope and tracked as a separate follow-up.

## Potential Solutions

### Option A: Split `isLoading` into "details loading" vs "background media loading"; fall back to first-frame thumbnail-as-background while video initializes
- **Approach:** Restructure each content viewmodel's `load*Details` (experience, gear, request, community, story) so it sets `isLoading: false` once the metadata fetch (entity details + owner + location + counts + `allMediaItems` thumbnail list) completes — *before* awaiting `_loadMediaFromServer(firstMediaId)`. Video download and `controller.initialize()` move to a fire-and-forget call. Add `isBackgroundMediaLoading` and `backgroundThumbnailUrl` fields to each freezed state. While the video controller is being set up, the view shows the **server-generated first-frame thumbnail JPEG** (already in `state.allMediaItems[0].thumbnailUrl`, produced by the #847 pipeline) as a still image background. Once the controller is initialized, state flips to the video player. The matching `*ContentView` widgets stop gating the entire view on `state.isLoading` for the media background and render the bottom content (title, chips, primary action) immediately.
- **Pros:** Matches the reviewer's exact ask — text is on screen as soon as metadata returns (~100ms), and the static "first frame" appears at the same moment with zero extra round-trip (the server already extracted that frame for the thumbnail). Architecturally clean: `MediaBackground` already renders images and video controllers separately, so the only widget change is choosing which to show. `getVideoFile()` already caches videos to disk, so a re-render (or scroll-back) is instant. Applying the change uniformly across all five viewmodels keeps the feed UX consistent (the reviewer's second ask) and lets us extract a single shared widget contract for `MediaBackground` rather than diverging per content type.
- **Cons:** Bigger PR than the previous narrowed scope: five viewmodels, five state classes (each freezed-regen'd), five content-view widgets. Two of the viewmodels (`gear`, `community`) use `safeUpdateState` from `SafeNotifierMixin`; the other three use the manual `if (!ref.mounted) return; state = state.copyWith(...)` pattern. Each file should keep its existing pattern — do not normalize. Behavior subtly changes for non-feed callers of every `*ContentView` (standalone screens, deep links) — they too will see text-first then video, which is arguably better but worth a deliberate decision. Does not address feed-wide video preloading (next-page video starts downloading only after the user swipes), so the *first* swipe to a new item still pays the full video latency before audio/motion start. That's an acceptable scope cut given the issue is about perceived feed slowness, not video latency itself.
- **Effort:** Medium-large (was Medium when scoped to experiences only).

### Option B: Aggressive preload — start downloading the next page's video while the current page is visible
- **Approach:** In `feed_screen.dart`, listen to `_onPageChanged` and proactively trigger media loading for the next 1-2 feed items via a new repository preload API. The current page still uses the same blocking `isLoading` gate, but by the time the user swipes, the video for the next page is already cached.
- **Pros:** Once warm, the feed feels instant for sequential swipes. Doesn't require state-machine changes to `ExperienceNotifier`.
- **Cons:** Doesn't help the *first* experience the user lands on (still slow). Doesn't help if the user swipes back to a non-adjacent page. Wastes data on videos the user never actually views. Doesn't address the reviewer's text-first ask — the spinner-on-the-current-page UX stays the same. Significantly more complex (needs a preload queue, cancellation when scrolling fast, memory management for keeping multiple `VideoPlayerController`s alive). High risk of regressions in chat/RSVP behavior because feed items may instantiate viewmodels outside the visible page.
- **Effort:** Large.

### Option C: Skip the video on the background until it's ready; show a static gradient or thumbnail and never auto-start
- **Approach:** Same as Option A's split, but never auto-initialize the video. Show the thumbnail. Only swap to video when the user explicitly taps a play button.
- **Pros:** Smallest code change (just gate the video-initialize call on a tap). Saves bandwidth on videos the user never watches. Better for low-end devices.
- **Cons:** Major UX regression — the current product experience is autoplay-on-scroll, similar to Reels/TikTok. Removing autoplay changes the feel of the feed entirely. The reviewer asked for "start the video once it's there," not "make the user tap to start." Out of scope for a perf fix.
- **Effort:** Small, but wrong product direction.

## Recommendation

**Option A, applied uniformly to all five item-detail surfaces in this PR** (`ExperienceContentView`, `GearContentView`, `RequestContentView`, `CommunityContentView`, `StoryContentView`). It directly implements the reviewer's stated fix — text-first, then static first-frame, then video — and reuses the server-generated thumbnail data already loaded in `allMediaItems` (no client-side first-frame extraction needed). Option B is a real improvement but solves a different problem (video latency on the very first frame, not perceived text latency) and is a larger lift; it remains a separate follow-up (Phase 3 below). Option C drops autoplay, which is not what the issue asks for.

Per reviewer direction, applying the change to all five content views in one PR keeps the feed UX uniform (mixed behavior across content types would itself be a perceived-quality regression) and shares the `MediaBackground` widget contract. Implementation order within the PR is: experience first (validates the pattern end-to-end), then gear/request/community/story (mechanical replication, smaller diffs once the pattern is set).

## Open Questions

- **Should we keep the spinner during the metadata fetch, or render skeleton text right away?** — Recommendation: keep the existing black-screen + spinner during the metadata fetch (~100ms typical). It's brief and matches the existing visual idiom; skeleton text would be over-engineering for a 100ms gap and inconsistent with how the rest of the app loads. If observed metadata fetch latency is high, revisit.
- **What does the screen show in the gap between "thumbnail rendered" and "video controller ready"?** — Recommendation: just the thumbnail (no spinner overlay). The user is reading the title/description anyway, and a spinner over the thumbnail is visual noise. The video appearing is its own affordance that something happened.
- **How do we handle videos that have no thumbnail (legacy data per #847)?** — Recommendation: the existing `MediaBackground` already shows black when `mediaPath` is null and the controller isn't ready. That's fine; we treat "no thumbnail" identically to current behavior — the bottom content still renders immediately, the background stays black until the video is ready. Confirm with a unit test.
- **Should `loadStats()` move earlier so impact stats are also in the first paint?** — Recommendation: no — it's already fire-and-forget after the await chain (`experience_view_model.dart:120`). Stats are not part of the perceived "is this content here yet" check. Leave it alone.
- **Do we need to handle the case where the user swipes away mid-load?** — Recommendation: the existing `if (!ref.mounted) return` checks plus `disposeMediaResources()` in the notifier's dispose hook already cover this. Verify no new races are introduced when the video init completes after the page is gone — the controller must be disposed, not assigned to dead state.
- **Should we apply the same fix to gear/request/community/story content views in the same PR?** — **Yes, per reviewer direction (PR #1473 review).** The reviewer asked for uniform behavior across all item detail screens. Keeping behavior consistent across the feed avoids a confusing "experience feels fast, gear feels slow" mixed UX. The state-machine differences between viewmodels (some use `SafeNotifierMixin.safeUpdateState`, others use the manual `if (!ref.mounted) return;` pattern) are handled by keeping each file's existing async-safety idiom rather than normalizing.
- **First frame vs JPEG thumbnail — is the server-generated thumbnail actually the first frame?** — Per #847, the thumbnail is server-extracted from the source video. Treat it as "first frame as static" for the purposes of this UX. If a future audit finds the extracted frame is not the literal first frame (some pipelines pick a representative frame later in the video), file a separate issue against the thumbnail pipeline; the client behavior in this plan does not need to change.

## Related Issues

- #847 — Server-side video thumbnail generation. The fix in this plan reuses thumbnail URLs that #847 establishes; videos without thumbnails fall back to existing black-background behavior, so we don't depend on #847 being closed.
- #821 — Story video background. Story content view shares the same blocking pattern; covered by Phase 2.
- #811 — Video caching. Disk caching of video files (`VideoFileCache` / `getVideoFile`) is what makes the second viewing of a video instant. This plan does not change the cache; it reorders when the cache is consulted relative to the rest of the UI.
- #929 — Broken videos. The thumbnail-fallback path in this plan should not regress error-handling for broken videos; ensure `loadMediaFromServer` failures still leave `isBackgroundMediaLoading: false` so the UI doesn't sit on a thumbnail forever.
- #1137 — Feed flash on minor update. Adjacent area; the silent-refresh path (`refreshWithoutLoadingSpinner`) used there sets the precedent for not flashing the spinner on subsequent loads.
