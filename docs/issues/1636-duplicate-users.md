# Issue #1636: Server allows duplicate users by email and phone number (causes EmailLogin 500s)

**Source:** https://github.com/Type2Fun-Foundation/ripls/issues/1636
**Filed:** 2026-05-01 | **Last activity:** 2026-05-01
**Labels:** none | **Assignees:** unassigned
**Context docs:** none

## Problem Statement

Production is returning HTTP 500 on `LoginService/EmailLogin` because the
`users` table has more than one row for the same email. The error surfaces in
`auth.UserManager.GetUserByEmail` (`server/auth/users.go:85-90`), which returns
an error whenever it sees `len(results) > 1`.

The duplicates exist because **none of the email-issuing registration RPCs
check for an existing row before inserting**:

- `EmailRegister` (`server/services/login/registration.go:23`) — inserts
  unconditionally at line 100 / via `completeRegistration` at line 94.
- `OIDCRegister` (`server/services/login/registration.go:132`) — inserts via
  `completeRegistration` at line 203, with no email lookup.

`PhoneRegister` (`server/services/login/phone_auth.go:34`) is the only
registration RPC that does the right thing — it calls `GetUserByPhone` first
and returns `CodeAlreadyExists` if a row is found (lines 56-63). So the
phone path is already protected on dedupe.

A secondary defect: emails are not normalized. There is no `ToLower` or
`TrimSpace` at any write or read site. That means `User@example.com` and
`user@example.com` are stored as distinct rows but neither will be found
when the user types the other variant at login.

The schema has no `UNIQUE` constraint on `email` or `phone_number` — the
`users` table is auto-generated by `protosql` from the proto descriptor
(`server/storage/protosql_schema.go:109-135`) and the generator only emits
a primary key on `id`. Per Bryan's comment on the issue, we are explicitly
**not** going to add a DB constraint; Go-level enforcement is sufficient.

Forensic example from prod (`ripls-prod`, revision `server-00081-42t`,
2026-04-30 20:33 UTC):
- `request_id` 00000000-0000-4000-8000-000000000005
- RPC `POST /ripls.api.LoginService/EmailLogin` → HTTP 500
- Masked email `su***@gmail.com`, 2 rows

The most likely creation path: user signed up with `EmailRegister` and later
came back through `OIDCRegister` (Google or Apple) using the same email.
Two rows, different `auth_method`. Any subsequent read by email — login,
password reset, OIDC login, or another register attempt — trips the duplicate
guard for that user forever, until the data is cleaned up.

## Context from Comments

One comment on the issue (from the maintainer):

> I don't think we need to complicate the schema, it seems sufficient to have
> go code that prevents duplicates.

This rules out the originally proposed DB-level unique index and folds the
work into a single Go-only fix. It also implies that the data-cleanup phase
does **not** need to gate on a migration — once the code blocks new duplicates,
cleanup of the existing duplicates can happen at any time.

No other comments. The issue and this plan are aligned with the maintainer's
direction.

## Potential Solutions

### Option A: Per-RPC dedupe checks + email normalization helper

- **Approach:** Add a `GetUserByEmail` call at the top of `EmailRegister`
  and `OIDCRegister`. Return `connect.CodeAlreadyExists` when a row is found.
  Introduce a single `normalizeEmail(string) string` helper
  (`strings.ToLower(strings.TrimSpace(email))`) and call it at every
  email read and write site (the four `GetUserByEmail` callers, the three
  user-creation paths, plus any password-reset email lookup).
- **Pros:** Mirrors the pattern already used by `PhoneRegister` — minimal
  novelty, easy to review, easy to test. Keeps the fix close to the bug.
  Phone path needs no behavior changes (Firebase returns E.164 already).
- **Cons:** Race window between the lookup and the insert is still open —
  two concurrent registers for the same email could both pass the precheck.
  In practice this is extremely unlikely (humans can't double-tap fast
  enough to slip both inserts inside one DB round trip), but it is not
  zero. Mitigations: a) accept the race, b) wrap the precheck + insert in
  a transaction with `SELECT ... FOR UPDATE`, c) catch a dup-key error from
  the DB. Bryan ruled out (c) by ruling out the unique index.
- **Effort:** Small.

### Option B: Centralize through `CreateOrUpdateFromOIDC`-style helpers

- **Approach:** Stop calling `storage.Insert` for users from the RPC layer.
  Instead, route every user creation through `auth.UserManager` methods that
  enforce the dedupe contract internally (one method per auth flow:
  `CreateEmailPasswordUser`, `CreateOIDCUser`, `CreatePhoneUser`). Each one
  normalizes inputs, checks for an existing row, and returns either the new
  user or `ErrUserAlreadyExists`.
- **Pros:** Future-proof. New registration paths inherit the contract for
  free. Brings the existing-but-unused `CreateOrUpdateFromOIDC` into a
  consistent pattern.
- **Cons:** Bigger surface change for a one-line bug. `completeRegistration`
  already does several things (insert, join community, record event,
  generate tokens) — splitting the user-create out cleanly would touch all
  three registration RPCs. Not justified for the immediate fix; could be a
  cleanup follow-up.
- **Effort:** Medium.

### Option C: Defense-in-depth — Option A plus a transactional precheck

- **Approach:** Option A, but the `EmailRegister`/`OIDCRegister` precheck +
  insert pair runs inside a single DB transaction, with the precheck using
  `SELECT ... FOR UPDATE` (or, more pragmatically, a serializable-isolation
  transaction). Closes the race entirely without a DB constraint.
- **Pros:** Strict guarantee even under concurrent registration.
- **Cons:** Adds transactional complexity to flows that don't otherwise need
  it. The race is theoretical for human-driven registration. Cost likely
  exceeds benefit.
- **Effort:** Medium.

## Recommendation

**Option A.** It directly mirrors `PhoneRegister`, ships in a small diff,
and matches the maintainer's "Go code that prevents duplicates" direction.
The race window is acceptable because (a) humans don't generate the load to
exploit it and (b) the prod incident we are fixing was caused by sequential,
not concurrent, registration. If we ever do see a concurrent-collision case
in logs, upgrading to Option C is a small follow-up.

Email normalization is non-negotiable and lives inside Option A — case- and
whitespace-variant emails should be the same identifier everywhere. Phone
numbers don't need a normalize helper because Firebase's
`VerifyPhoneToken` already returns E.164 (`server/auth/firebase.go:38-62`).

## Open Questions

- **Should the normalization happen inside `auth.UserManager` (every
  read and write) or at the RPC boundary (in handlers, before delegating)?**
  Recommendation: inside `auth.UserManager`. That single chokepoint owns
  email→user lookups; normalizing there means we cannot accidentally bypass
  it from a new caller. Handlers should still trim+lower the user-supplied
  email before storing it on `models.User.Email` so the persisted value
  matches the lookup key.
- **What error code should the precheck return — `AlreadyExists`, or
  something more user-actionable like `InvalidArgument` with a message
  steering the user to login?** Recommendation: `CodeAlreadyExists`. That's
  what `PhoneRegister` returns and what gRPC conventions expect; the client
  can map it to the "use a different email or sign in" UX.
- **Should we also reject emails that match an existing row of a *different*
  auth method (e.g., new OIDC register where an EmailPassword row already
  exists for that email), or only same-method?** Recommendation: reject
  unconditionally. Allowing two rows for the same email is the bug; the
  registered user can recover via the existing-method's login flow or via
  password reset. The friendly error message can mention which method the
  account was registered with.
- **Should the dedupe check exclude soft-deleted users?** Recommendation: yes.
  A user who was soft-deleted (`Deleted` set on `models.User`) and tries to
  register again should not be blocked by their old row. `GetUserByEmail`
  today does a raw `QueryByField` that doesn't filter soft-deleted rows,
  so the precheck needs either (a) a new `GetActiveUserByEmail` helper that
  filters `WHERE deleted_at_unix_sec IS NULL`, or (b) caller-side filtering
  on the returned user. Prefer (a) so the contract is clear and reusable.
  Audit existing callers (`EmailLogin`, `OIDCLogin`, `RequestPasswordReset`)
  to decide whether they should switch to the new helper too — login
  against a soft-deleted user should probably fail with `Unauthenticated`,
  matching the "account doesn't exist" UX.
- **Do we backport this fix to any release branches?** Recommendation:
  `main` only. The duplicates already in prod will keep failing reads until
  cleanup runs (separate issue), so cherry-picking to a release branch
  doesn't change the user-visible outcome. Cut a normal release.
- **Tests: is there a real-Postgres harness for login flows already?**
  Recommendation: yes — `storage.SetupTestStorage(t)` per CLAUDE.md. The
  duplicate scenarios should be integration tests (using a real DB) rather
  than mocks, since the bug class is about persistence behavior.

## Implementation Plan

### Phase 1: Add dedupe checks and normalize email in registration paths

**Goal:** Make it impossible for `EmailRegister` and `OIDCRegister` to
create a second `users` row for an email that already exists, and make
case/whitespace variants of the same email collide.

**Tasks:**
- [ ] Add `normalizeEmail(string) string` in `server/auth/users.go`
      (`strings.ToLower(strings.TrimSpace(email))`).
- [ ] Apply `normalizeEmail` inside `UserManager.GetUserByEmail` before the
      `QueryByField` call (`server/auth/users.go:72`).
- [ ] Apply `normalizeEmail` to `User.Email` inside `UserManager.CreateUser`
      and `CreateOrUpdateFromOIDC` so persisted values match the lookup key.
- [ ] Add `UserManager.GetActiveUserByEmail` that filters out soft-deleted
      rows. Use it from the registration prechecks; leave `GetUserByEmail`
      alone for callers that need the raw view (or migrate them in the same
      PR — see follow-up audit task below).
- [ ] In `EmailRegister` (`server/services/login/registration.go:23`):
      normalize `req.Msg.Email`, call `userManager.GetActiveUserByEmail`,
      return `connect.CodeAlreadyExists` with a message naming the existing
      `auth_method` if a row is found, otherwise proceed.
- [ ] In `OIDCRegister` (`server/services/login/registration.go:132`):
      same precheck against `userInfo.Email` after normalization, before
      `completeRegistration`.
- [ ] Log each duplicate-rejection at `WARN` (not `ERROR`) — duplicate
      registration is a user error per `docs/server/observability.md`
      §"Appropriate Log Levels". Use `logging.LoggerWithContext(ctx)` with
      fields `operation`, `user_email` (via `logging.MaskEmail`),
      `auth_method`, and `existing_auth_method`.
- [ ] **Do not** change the existing `ERROR` log at `server/auth/users.go:86`.
      That log is the alert tripwire that surfaced this bug; it must stay
      loud so any remaining legacy duplicates (or a future regression of
      the dedupe check) keep paging us. (See feedback memory:
      "Keep ERROR logs for unexpected conditions — don't downgrade to
      silence alerts.")
- [ ] Audit the other email read sites — `EmailLogin`
      (`authentication.go:27`), `OIDCLogin` (`authentication.go:125`),
      `RequestPasswordReset` (`password_reset.go:29`) — to confirm they
      pick up normalization automatically through `UserManager`. Decide
      per-site whether they should also switch to `GetActiveUserByEmail`
      (recommend yes for `EmailLogin`/`OIDCLogin`; password reset should
      probably also exclude deleted users).
- [ ] Confirm `PhoneRegister` needs no behavior change (already dedupe-checks).

**Validates:** Prod log query
`jsonPayload.message="multiple users found with same email"` from a
registration path returns zero new entries after deploy. (Existing duplicate
rows still trip the read path until Phase 3 cleanup runs — that's a feature,
not a bug, until the data is fixed.)

### Phase 2: Tests

**Goal:** Lock down the new behavior so a future refactor cannot regress it.
Per `docs/server/architecture.md` §"Testing Strategy": unit tests for the
helper, integration tests (real Postgres via `storage.SetupTestStorage(t)`)
for the duplicate scenarios, since the bug class is about persistence
behavior and exact-match collisions need real SQL.

**Tasks:**
- [ ] Unit tests for `normalizeEmail` in `server/auth/users_test.go`
      (table-driven: trim, lower, mixed-case, surrounding whitespace,
      idempotence, empty input, unicode).
- [ ] Unit tests for `UserManager.GetActiveUserByEmail` in
      `server/auth/users_test.go` (returns nil for soft-deleted, returns
      user for active, normalizes input).
- [ ] Integration tests in `server/services/login/registration_test.go`
      using `storage.SetupTestStorage(t)`:
      - Two sequential `EmailRegister` calls with the same email → second
        returns `CodeAlreadyExists`, only one row in DB.
      - `EmailRegister` then `OIDCRegister` with the same email → second
        returns `CodeAlreadyExists`.
      - `OIDCRegister` then `EmailRegister` with same email → second
        returns `CodeAlreadyExists`.
      - Case- and whitespace-variant emails collide on register and login
        (`Foo@Example.com` registered, ` foo@example.com ` attempt →
        `AlreadyExists`; subsequent `EmailLogin` with either variant
        succeeds).
      - Re-register after soft-delete of the prior row succeeds (validates
        the `GetActiveUserByEmail` filter).
- [ ] Regression guard in `server/services/login/phone_auth_test.go`:
      `PhoneRegister` still returns `AlreadyExists` for an already-registered
      phone (in case the new shape of `auth.UserManager` accidentally
      affects it).

**Validates:** All five duplicate scenarios fail without the Phase 1 changes
and pass with them. `npm run build` (golangci-lint + `go build`) and
`go test ./...` both green.

### Phase 3: Data cleanup (track in a separate issue)

**Goal:** Resolve the existing duplicate rows so that affected accounts can
log in again. Not in scope for this PR — file a follow-up.

**Tasks:**
- [ ] Open follow-up issue with the cleanup query and proposed merge policy
      (keep oldest, soft-delete newer; reassign owned gear, communities,

- [ ] Cleanup script runs once against prod after Phase 1+2 ship.

**Validates:** Affected user `su***@gmail.com` (and any others surfaced by

## Architecture Compliance

This plan was audited against the server architecture and observability
guides. Key alignment points:

- **Service Independence (`docs/server/architecture.md` §74-87):** All new
  logic lives inside `auth.UserManager` (the shared library). Login
  service uses the manager rather than reaching into storage directly.
- **Error wrapping (`docs/server/architecture.md` §926-940):** The plan
  uses `connect.NewError(connect.CodeAlreadyExists, ...)` for the user-
  visible duplicate response. `connecterr.Internal` is reserved for
  internal failures and is not the right tool here. No bare
  `connect.NewError(connect.CodeInternal, err)` is introduced.
- **Structured logging (`docs/server/observability.md` §"Appropriate Log
  Levels"):** Duplicate-registration rejections log at `WARN` (user
  errors are not `ERROR`). Use `logging.LoggerWithContext(ctx)`,
  `logging.MaskEmail()`, and the standard fields `operation`,
  `user_email`, `auth_method`.
- **ERROR-log preservation:** The existing `users.go:86` `ERROR` log
  stays. Per the user's recorded feedback, ERROR logs that surface real
  data-integrity bugs must remain loud — don't downgrade to silence the
  alert; fix the upstream cause (which is exactly what this PR does).
- **Testing strategy (`docs/server/architecture.md` §163-209):** Unit
  tests for the helper, integration tests with `storage.SetupTestStorage(t)`
  for the persistence scenarios. Test files sit alongside implementation
  per convention.
- **Schema compliance:** Per Bryan's comment, no DB-level constraints are
  introduced; the proto-driven `protosql` schema is left untouched.
