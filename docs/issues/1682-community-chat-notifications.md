# Issue #1682: No chat message notifications for community wide chat

**Source:** https://github.com/Type2Fun-Foundation/ripls/issues/1682
**Filed:** 2026-05-03 | **Last activity:** 2026-05-03
**Labels:** user-feedback | **Assignees:** unassigned
**Context docs:** none (predecessor plans: [docs/issues/1637-community-wide-chat.md](1637-community-wide-chat.md), [docs/issues/1650-community-chat-followups.md](1650-community-chat-followups.md))

## Problem Statement

Push notifications are not being delivered for messages sent in **community-wide chat** conversations (the Discuss tab introduced by #1637 / PR #1646). Direct/topic-scoped chats (transfer, request, gear, experience) still notify their participants normally — only the community-wide variant is silent.

The bug is server-side and structural, not a delivery flake. Community-wide conversations were intentionally created with an **empty `ParticipantIds` list** in [`server/chat/conversations.go:75`](../../server/chat/conversations.go#L75) (`CreateCommunityConversation` sets `ParticipantIds: []string{}`) under the design "Participants are resolved dynamically from community membership" ([line 150-151](../../server/chat/conversations.go#L150)). The read path honors that contract — [`GetConversation` at `server/services/chat/conversations.go:289-301`](../../server/services/chat/conversations.go#L289) explicitly substitutes a community-membership check for the participant-list check and never adds the reader to `ParticipantIds`.

But the **notification dispatcher** ([`server/services/chat/notifications.go:55-70`](../../server/services/chat/notifications.go#L55)) fans out by iterating `conversation.ParticipantIds`. For community-wide conversations that list is permanently empty, so the loop body never runs and no FCM push is ever queued. The message is persisted, the live stream broadcast still works (so users with the app open and the Discuss tab focused see it in real time), but anyone who isn't already streaming the conversation gets nothing.

This is a regression introduced by the community-wide-chat MVP (#1637 / PR #1646) — the dispatcher was never updated for the "dynamic participants" topology.

## Context from Comments

The issue has no comments. It was filed today (2026-05-03) by the project lead from a Pixel 9 Pro on PROD app version 0.19.0 build 6338. The bug report is purely descriptive ("No push notifications seem to be sent for chat messages in community-wide chats") with no repro steps, but the report is precise enough that no clarification is needed — community-wide chat is a single, well-defined surface and the symptom is unambiguous.

No comments means no maintainer pushback or revised requirements; the original framing stands.

## Current State Snapshot

Useful baselines from the codebase research that the recommendation depends on:

- **`CreateCommunityConversation`** ([`server/chat/conversations.go:36-88`](../../server/chat/conversations.go#L36)) is the sole entry point that creates a community-wide `ChatConversation`. It hard-codes `ParticipantIds: []string{}` ([line 75](../../server/chat/conversations.go#L75)) and explicitly comments at [line 150](../../server/chat/conversations.go#L150) that "Community conversations are open to all community members; membership check replaces the participant list (participants are dynamic)."
- **The read-path branch** at [`server/services/chat/conversations.go:289-301`](../../server/services/chat/conversations.go#L289) confirms the same contract on the read side: when `topic.GetCommunityId() != ""`, it calls `auth.IsMemberOfCommunity` instead of consulting `ParticipantIds`, sets `isParticipant = true` if the membership check passes, and **never adds the user to `ParticipantIds`**.
- **`notifyParticipants`** ([`server/services/chat/notifications.go:15-184`](../../server/services/chat/notifications.go#L15)) is the fan-out function. Its core loop at [line 70](../../server/services/chat/notifications.go#L70) (`for _, participantID := range conversation.ParticipantIds`) is the bug site. Everything inside that loop body — preference gates, foreground/stream suppression, sender lookup, payload build, FCM dispatch — is correct; it just never executes for community-wide chat.
- **`community.FetchPreferencesForUsers`** ([`server/community/notifications.go:171-176`](../../server/community/notifications.go#L171)) is exported and already used by `notifyParticipants` to batch-fetch the per-community "Chats" preference. It accepts an arbitrary recipient list — no change needed for fan-out resolution.
- **`getCommunityMemberIDs`** ([`server/community/notifications.go:769-789`](../../server/community/notifications.go#L769)) is the existing helper that fetches all `CommunityUser` rows for a community and returns the user IDs. It is **package-private** today — only called by the community-event dispatcher inside the same file. To reuse it from `server/services/chat/notifications.go`, it needs to be exported (or duplicated; exporting is cheaper and keeps one canonical path).
- **Community-event fan-out** at [`server/community/notifications.go:417`](../../server/community/notifications.go#L417) already does the equivalent fan-out for community events: resolves all members, then `FetchPreferencesForUsers` for the same community. So the chat fix is a structural replication of an existing, working pattern — not a new design.
- **Per-user gates inside the loop** apply correctly regardless of whether the recipient list comes from `ParticipantIds` or community membership: don't notify the sender, gate on `community.CategoryEnabled(prefs[uid], NOTIFICATION_CATEGORY_CHATS)`, suppress when `hasActiveStream && isUserInForeground`, suppress when `!hasDevices`. None of these need to change.
- **The soft-delete community gate** at [line 33-39](../../server/services/chat/notifications.go#L33) already runs **before** the participant loop, so it remains correct under any fan-out source.
- **Mention handling** at [`server/services/chat/mention_handler.go:102`](../../server/services/chat/mention_handler.go#L102) does `conversation.ParticipantIds = append(conversation.ParticipantIds, usersToAdd...)` to add mentioned users not yet in the conversation. For community-wide conversations this means a mentioned user gets persistently added to `ParticipantIds` — they are then visible via `ListByParticipant`, which is how community conversations show up in their inbox at all. That mechanism still works; the fix here doesn't disturb it.
- **`ListByParticipant`** ([`server/storage/chat_conversation.go:96`](../../server/storage/chat_conversation.go#L96)) is what the inbox uses to find a user's conversations. Community-wide conversations only show in the inbox after the user posts (which adds them via the existing path) or is mentioned. **This is a separate, related issue but out of scope here**: a passive lurker who never posts/gets mentioned won't see the conversation in their inbox via `ListByParticipant`. The notification fix won't change that — but if we send notifications to everyone, a lurker who taps the push will deep-link straight into the conversation regardless of inbox visibility (the deep-link path uses `GetConversation`, which uses the membership check, not `ListByParticipant`). Flag in Open Questions.
- **No existing test exercises the community-topic branch of `notifyParticipants`.** The two existing tests (`TestNotifyParticipants_DeletedCommunityGate` and `TestNotifyParticipants_ActiveCommunityStillNotifies` in [`server/services/chat/notifications_test.go`](../../server/services/chat/notifications_test.go)) seed conversations with `ParticipantIds: []string{senderID, recipientID}` — i.e., topic-scoped, not community-wide. The dispatcher's community-wide path is currently untested.
- **Test infra**: the chat tests already use `storage.SetupTestStorage(t)` and `mockNotificationService`; community-membership seeding via `models.CommunityUser` rows is straightforward (the equity tests do it widely).

## Potential Solutions

### Option A: Fan out to community membership when the conversation's topic is `CommunityId` (recommended)

- **Approach:** In `notifyParticipants`, branch on the conversation topic before the participant loop. If `conversation.Topic.GetCommunityId() != ""` (community-wide), resolve recipients from `community.GetCommunityMemberIDs(ctx, s.storage, conversation.CommunityId)` instead of `conversation.ParticipantIds`. Otherwise use `conversation.ParticipantIds` as today. Export `getCommunityMemberIDs` → `GetCommunityMemberIDs` so the chat package can call it. All downstream gates (sender skip, prefs, stream/foreground, devices) remain unchanged.
- **Pros:** Mechanical change. Mirrors the community-event dispatcher pattern that already works at scale. Single, narrow code path. Doesn't disturb the "dynamic participants" design — `ParticipantIds` stays empty, and the membership lookup happens at notification time. Test surface is small and crisp.
- **Cons:** A second source-of-truth for "who's in this conversation" — but only at notification time; reads still go through the membership check; sends still write `ParticipantIds: []`. Per-message DB query to `community_user` for membership; mitigated by fact that this is already how community events fan out (so per-event cost is comparable).
- **Effort:** Small.

### Option B: Materialize community members into `ParticipantIds` at chat-conversation creation time, and keep it in sync as members join/leave

- **Approach:** When `CreateCommunityConversation` runs, populate `ParticipantIds` with all current community members. Hook `JoinCommunity` / leave / removal flows to add/remove from the conversation's `ParticipantIds`. The read path still uses the membership check (so authorization is unchanged), but the dispatcher loop "just works" without a topic branch.
- **Pros:** No dispatcher change at all — the existing loop handles community chat for free. Inbox via `ListByParticipant` would also start to surface community conversations to all members (sidesteps the lurker-inbox problem mentioned in the snapshot above).
- **Cons:** Adds a new invariant that the codebase didn't have — community conversation `ParticipantIds` must mirror `community_user`. Every membership-change RPC (join, leave, remove, ban, unban) needs to keep `ParticipantIds` in sync, including soft-delete/restore paths. New backfill needed for existing community conversations created with the empty list. Drift risk: any future RPC that mutates membership without remembering to update the conversation re-introduces the bug. The "dynamic participants" comment at [conversations.go:150](../../server/chat/conversations.go#L150) becomes a lie. **And it changes inbox semantics** for users who never posted in the community — surfacing every community's chat in every member's inbox is a separate product question that #1650 is already grappling with via the unread-count gate.
- **Effort:** Medium. Touches multiple services (community join/leave, ban/unban, soft-delete, restore), needs a backfill job, and changes inbox surface area.

### Option C: Fan out to "people who have ever streamed or posted" (subscriber-style)

- **Approach:** Track per-user "interest" in a community conversation (any user who streams the conversation or posts a message gets recorded), and notify only that set on new messages.
- **Pros:** Smaller fan-out than full community membership — only people who have shown interest get pinged.
- **Cons:** Means a member who has never opened the Discuss tab gets no notification ever — including the very first message of a thriving conversation, which is precisely the case where notification is most valuable to drive discovery. Adds a new "subscriber" data structure that doesn't exist today. Underdelivers compared to user expectation ("I'm in the community → I get its chat notifications, modulo the per-community Chats preference toggle").
- **Effort:** Medium-large.

## Recommendation

**Option A.** Add a topic-branch in `notifyParticipants` that resolves community-wide recipients from `community_user` instead of `ParticipantIds`. Export `GetCommunityMemberIDs` from `server/community/notifications.go`. All the existing per-recipient gates (sender skip, Chats-preference gate, stream/foreground suppression, device check) operate identically on the resolved set.

Reasons to prefer A over B:

- **Bounded blast radius.** The change is one branch in one function plus an export of one helper. B touches many files and adds a long-lived invariant.
- **Honors the existing design.** The code at [conversations.go:148-151](../../server/chat/conversations.go#L148) deliberately models community conversations with dynamic membership. Option A reads that design at notification time; Option B contradicts it.
- **Mirrors a working pattern.** Community-event fan-out already does exactly this (resolve members + `FetchPreferencesForUsers`), at presumably-larger frequencies, without issue. The chat dispatcher should match.
- **Inbox visibility is a separate problem.** Option B's "inbox-surfaces-for-everyone" side effect is **not** something we should bundle into a notification fix; #1650 already considered surfacing community chats in the inbox and chose an unread-count gate, not a participant-list change.

Reasons to prefer A over C:

- **Matches user mental model.** "I'm in this community → I get notified" is the default expectation; the per-community "Chats" toggle is the off-switch users already understand.
- **No new state surface.** C would need a new "interested users" relation that doesn't exist.

## Open Questions

- **Inbox visibility for lurkers.** A user who has never posted in (and was never mentioned in) a community-wide conversation will get notifications under this fix, but their inbox doesn't currently list the conversation (because `ListByParticipant` filters on `ParticipantIds`, which they're not in). Tapping the push deep-links them directly to the conversation, which works, so it's not a hard break — but it's a UX inconsistency: "I got a push, why isn't it in my inbox until I read it?" — Recommendation: ship the notification fix first (it's the user-reported bug), and file a separate follow-up to make community conversations appear in the inbox of any community member who has unread messages, gated by `unreadCount > 0` (parity with the #1650 inbox-row design). Don't widen this issue's scope; keeping the participant-list contract intact is part of why Option A is small.
- **Fan-out scale.** For a 5,000-member community, every chat message triggers a `community_user` query plus a `FetchPreferencesForUsers` query, then up to 5,000 per-user `HasDevices` and `NotifyUser` calls. The existing community-event dispatcher already operates at this scale, so we have a precedent — but chat is higher-volume than events. — Recommendation: ship as-is, since it matches the community-event pattern, and plan to add an FCM topic-based fan-out (subscribe each device to a per-community topic, send one fanout to FCM, let FCM multiplex) as a future optimization if production load shows it's needed. Not a launch blocker; the existing per-user dispatch path is correct, just not the most efficient. Track via a follow-up if observed.
- **Throttling / digesting bursts.** A chatty community with 1,000 members and 50 messages an hour produces 50,000 pushes/hour from this fix. Existing topic-scoped chats don't have this multiplier (they fan to ~2 people each), so the existing dispatcher has never had to think about it. — Recommendation: do **not** add throttling or digest behavior in this issue — the user-reported bug is "no notifications at all", and fixing that is the priority. File a follow-up to explore "Chats" preference granularity (e.g. per-conversation mute, quiet hours, digest mode) once we have any production data on community chat volume. Mention in the launch checklist that we should monitor FCM dispatch volume after deploy.
- **`hasActiveStream` correctness for community conversations.** The existing `hasActiveStream(conversation.Id, participantID)` check should already work for community-wide conversations — it's keyed on `(conversationID, userID)` regardless of how the user "joined". — Recommendation: verify this in a unit test (assert that streaming users do not receive a notification under Option A's flow) but expect no behavior change is needed.
- **Backfill / catch-up notifications.** The bug has existed since #1637 / PR #1646 shipped. We're not going to retroactively notify users about messages they missed. — Recommendation: no backfill needed; the fix is forward-only. Flag in the PR description so reviewers understand.

## Implementation Plan

### Phase 1: Server fix — fan out community-wide chat to community membership

**Goal:** A new chat message in a community-wide conversation generates push notifications to every community member who (a) is not the sender, (b) has the per-community "Chats" preference enabled (or unset), (c) is not actively streaming the conversation in the foreground, and (d) has at least one registered device.

**Tasks:**

- [ ] **Export `GetCommunityMemberIDs`.** Rename [`getCommunityMemberIDs` at `server/community/notifications.go:769-789`](../../server/community/notifications.go#L769) to the exported name. Update its single existing caller in the same file. The helper's body and signature stay otherwise unchanged. Function comment updated to start with the symbol name per [CLAUDE.md](../../CLAUDE.md) `revive.exported` rule.
- [ ] **Branch on conversation topic in `notifyParticipants`.** In [`server/services/chat/notifications.go:54-59`](../../server/services/chat/notifications.go#L54), where `participantsToFetch` is currently built from `conversation.ParticipantIds`, branch on the topic:
  - If `conversation.Topic.GetCommunityId() != ""` → call `community.GetCommunityMemberIDs(ctx, s.storage, conversation.CommunityId)`, then build `participantsToFetch` from that result minus the sender. On query error: emit `logger.WarnContext(ctx, "failed to resolve community members for chat fan-out", "error", err)` and **return** (fail-closed for community-wide). Update the surrounding loop's source-of-truth correspondingly — i.e., switch the outer `for _, participantID := range conversation.ParticipantIds` to iterate the resolved set. The simplest shape is to compute a single `recipientIDs []string` slice up-front (one branch for community-wide → membership query, else → `conversation.ParticipantIds`), and then have one loop body downstream.
  - **Fail-closed vs. fail-open rationale.** The existing prefs-fetch error handler at [line 60-68](../../server/services/chat/notifications.go#L60) deliberately fails **open** (treat preference as on for everyone) because under-delivery is the worse failure for chat. The membership-resolution path takes the opposite stance: failing **closed** is correct because there is no sensible default recipient list to fall back to — the alternative is dispatching to nobody anyway, since `ParticipantIds` is empty for community-wide. The WARN log surfaces the failure to alerting (per `Server Error Logged` policy in [docs/server/observability.md](../../docs/server/observability.md) §"Alert Policies"); we don't escalate to ERROR because the user-facing failure (no push) is identical to the natural state of an under-loaded community and shouldn't page on-call. Per [CLAUDE.md](../../CLAUDE.md) §"Fail Fast", this is a documented exception: the dispatcher runs in `GoSafe` (async), errors can't propagate to the caller anyway, and the WARN log + alert rule are the documented escape hatch.
  - **All downstream gates remain unchanged:** sender skip, `prefsByUser[participantID]` lookup, `community.CategoryEnabled(..., NotificationCategory_NOTIFICATION_CATEGORY_CHATS)`, `hasActiveStream + isUserInForeground` suppression, `notificationService.HasDevices`, `senderName / previewText` build, `chatPayload` construction, `notificationService.NotifyUser` dispatch.
- [ ] **Soft-delete gate stays first.** The community-soft-deleted gate at [line 33-39](../../server/services/chat/notifications.go#L33) runs **before** the recipient resolution and stays correct under either branch. Verify no reordering breaks it.
- [ ] **`NotifyChatMessage` wrapper inherits the fix automatically.** The public wrapper at [`server/services/chat/service.go:85-87`](../../server/services/chat/service.go#L85) (which exists to satisfy the `MessageNotifier` interface used elsewhere — e.g., system-message dispatch from outside the chat service) just delegates to `notifyParticipants`. No change needed there; the topic branch covers all entry paths.
- [ ] **Logging.** When the community-wide branch fires, add a `logger.DebugContext(ctx, "fanning out community-wide chat notification", "community_id", conversation.CommunityId, "recipient_count", len(recipientIDs))` line so production logs can show the fan-out size. Per [docs/server/observability.md](../../docs/server/observability.md) §"Logging Usage Pattern", use the `*Context` form (`DebugContext` / `WarnContext`) — never the bare `Debug` / `Warn` form — so the request_id propagates. Note that the existing call at [line 62](../../server/services/chat/notifications.go#L62) uses the bare `logger.Warn` form; that's a pre-existing inconsistency we don't need to fix in this issue, but new logging in the same function should use the documented form. Field-naming follows the standard table in observability.md §"Standard Field Names": `community_id`, `conversation_id`, `message_id` are already on the logger; `recipient_count` is a custom field (allowed by the same doc's "Entity-specific fields follow patterns" guidance).
- [ ] **No proto / RPC changes.** This is purely a server-internal fix. The wire format for `Notification`, `ChatMessagePayload`, `ChatConversation`, etc. is unchanged.
- [ ] **No client changes.** The Flutter app handles incoming `ChatMessage` payloads identically regardless of conversation topic — `ChatMessagePayload` already carries `community_id` and the deep-link path in `community_chat_pane.dart` is the same one experience/request use. Confirm by inspection only; no code touched.
- [ ] **Tests** ([CLAUDE.md](../../CLAUDE.md) §"Server Testing"): add to [`server/services/chat/notifications_test.go`](../../server/services/chat/notifications_test.go):
  - `TestNotifyParticipants_CommunityWide_FansOutToMembers` — seed a community with 3 members (sender + 2 others, all with devices), seed a community-wide conversation with `ParticipantIds: []string{}` (empty, matching production state), call `notifyParticipants` for a user message from the sender → assert exactly 2 `NotifyUser` calls, one per non-sender member. Verifies the core fix.
  - `TestNotifyParticipants_CommunityWide_SkipsSender` — same setup but assert sender is **not** in the dispatched recipients. (Subset of the above but worth an explicit single-assertion test for clarity.)
  - `TestNotifyParticipants_CommunityWide_RespectsChatsPreferenceGate` — seed two members, one with the Chats preference disabled for that community (set `ChatsEnabled: false` or whatever the preference field is on `CommunityUserNotificationPreference`) → assert only the enabled member receives a push.
  - `TestNotifyParticipants_CommunityWide_SkipsStreamingForegroundUsers` — seed two members; mark one as having an active stream + foreground via the same hooks the existing tests use → assert that user is skipped, the other is dispatched.
  - `TestNotifyParticipants_CommunityWide_SkipsUsersWithoutDevices` — seed two members, only one with a registered device → assert one dispatch.
  - `TestNotifyParticipants_CommunityWide_SoftDeletedCommunityStillSkipped` — community soft-deleted, conversation has community-topic → assert zero dispatches (validates the soft-delete gate fires before the new fan-out branch).
  - `TestNotifyParticipants_CommunityWide_MembershipQueryFailureWarnsAndDispatchesNothing` — induce a query error (or assert by inspection if a clean injection point doesn't exist; otherwise document why this branch is best-tested by code review) → no panic, log emitted, no dispatches.
  - **Existing tests stay green.** The two existing tests use topic-scoped (transfer/request) conversations with non-empty `ParticipantIds`; they hit the unchanged branch. Verify both still pass.
- [ ] **N+1 / SQL hygiene.** The new fan-out adds **one** `community_user` query (`GetCommunityMemberIDs` calls `QueryByField`) per chat message in a community-wide conversation. The existing community-event dispatcher does the same query at the same cost. No N+1 introduced. Per [CLAUDE.md](../../CLAUDE.md) §"SQL Efficiency", verify with `storage.AssertMaxQueries(t, ctx, max, fn)` in one of the new tests if a clean test point exists; otherwise rely on inspection.
- [ ] **Unbounded query footprint (existing).** `GetCommunityMemberIDs` calls `QueryByField` without a LIMIT — for a 5,000-member community it returns all 5,000 rows. This is a pre-existing footprint shared with the community-event dispatcher (which already runs at this scale in production); we are not introducing it. Per [CLAUDE.md](../../CLAUDE.md) §"SQL Efficiency" rule 3 ("Always LIMIT unbounded queries"), this is a known gap worth tracking but **not** a precondition for this fix — adding a LIMIT here without a paginated dispatch loop would silently under-deliver to large communities, which is worse than the current behavior. File a follow-up issue to add a paginated `IterateCommunityMembers(ctx, communityID, batchSize, fn)` helper that the chat and community-event dispatchers can both consume, replacing the single-shot `QueryByField` in both places at once.
- [ ] **`npm run build`** clean (lint + `go build ./...`). Per [CLAUDE.md](../../CLAUDE.md), since this changes function exports (renaming a private helper to public) but doesn't touch any signature an `integration`-tagged test calls, `go build -tags=integration ./...` is **not** required, but cheap to run as a sanity check.

**Validates:** A community-wide chat message in a community with N members generates N-1 push notifications (modulo the prefs/stream/foreground/devices gates). Topic-scoped chats are unaffected. No existing tests regress.

### Phase 2: End-to-end verification on emulator + production-like dataset

**Goal:** Confirm the fix lands cleanly on real Android (the device the bug was filed on) and iOS, and that no preference / stream / payload edge case slipped through.

**Tasks:**

- [ ] On Android emulator + iOS simulator: two test users in the same community, both with notifications enabled. User A sends a message in community Discuss tab. User B (app backgrounded) receives push. Tapping the push lands B on the Discuss tab of the community.
- [ ] Repeat with B in foreground but on a different screen (not actively streaming the conversation) → B receives push.
- [ ] Repeat with B in foreground **and** actively viewing the Discuss tab → B does **not** receive a push (foreground-streaming suppression; this is the same path topic-scoped conversations use).
- [ ] Repeat with B's "Chats" preference for that community disabled → B does **not** receive a push.
- [ ] Repeat with no registered devices → no push attempted (log only).
- [ ] **Cross-community noise check:** B is in two communities, A sends to community 1 only → B receives one push, not two; verify the `community_id` in the payload matches the source community.
- [ ] **Deep-link payload:** the `ChatMessagePayload` in the push contains `conversation_id`, `message_id`, `sender_user_id`, `sender_name`, `preview_text`, and `community_id`. No topic-entity (gear/experience/request/transfer) IDs are populated for community-wide chat — confirm by inspecting the actual FCM payload (use the [`ripls-app-logs`](../../.claude/skills/ripls-app-logs/SKILL.md) skill to capture).
- [ ] **Dispatch volume monitoring** (post-deploy, not a code task): after the fix ships, watch FCM-dispatch logs for one chatty community for a few hours. Confirm the per-message dispatch count is approximately `(member_count - 1) - (members_streaming_in_foreground) - (members_with_chats_disabled)`. Order-of-magnitude is what matters here — if the volume is implausibly high, that's the trigger to revisit the throttling open question.
- [ ] **Mention overlap regression check.** A message that @-mentions a member of the community → only one push to that member (not two: one from the membership fan-out, one from the mentions path). Confirm by inspecting the existing mention path: mention handler appends to `ParticipantIds` *before* `notifyParticipants` runs ([`server/services/chat/messages.go:156`](../../server/services/chat/messages.go#L156) shows `notifyParticipants` is called with `mentionedUserIDs...` after the message is inserted). Under Option A's branch, for community-wide conversations we ignore `ParticipantIds` and use community membership instead — so a mentioned member who is also a community member appears in the recipient set exactly once, gets the "X mentioned you" title, and receives one push. Verify with a unit test in Phase 1 if not already covered: `TestNotifyParticipants_CommunityWide_MentionedMemberGetsMentionTitle`.

**Validates:** Real-device behavior matches the unit-test contract. No double-notification, no missed notification under any common configuration.

[docs/client/*](../../docs/client/) reviewed and confirmed not applicable — this fix is entirely server-side; no proto, RPC, viewmodel, repository, service-client, ARB, a11y, or navigation change.

**Changes made during audit:**

1. **Logging method form pinned to `*Context` variants.** Original Phase 1 task said `logger.DebugContext(ctx, ..., "community_id", ..., "recipient_count", len(recipientIDs))` for the new fan-out log line, but did not address the warning emitted on membership-resolution failure. Per [docs/server/observability.md](../../docs/server/observability.md) §"Logging Usage Pattern", all new logging in functions with a context should use the `*Context` form so `request_id` propagates. Updated to specify `logger.WarnContext(ctx, "failed to resolve community members for chat fan-out", "error", err)`. Also called out (without scope-creep) that the existing bare `logger.Warn` at [notifications.go:62](../../server/services/chat/notifications.go#L62) is a pre-existing inconsistency we don't fix in this issue, so a reviewer doesn't ping us on the asymmetry.

2. **Fail-closed semantics made explicit.** Original Phase 1 said "fail-closed for community-wide is acceptable" without contrasting it against the existing fail-open prefs handler immediately above it in the same function. Added an explicit "Fail-closed vs. fail-open rationale" sub-bullet that (a) names the existing fail-open pattern at line 60-68, (b) explains why prefs has a sensible default but membership doesn't, (c) cites [CLAUDE.md](../../CLAUDE.md) §"Fail Fast" as the documented-exception standard and points to the WARN→alert chain in [docs/server/observability.md](../../docs/server/observability.md) §"Alert Policies" as the escape hatch. This pre-empts a likely review comment.

3. **`NotifyChatMessage` wrapper coverage called out.** The plan didn't mention the public wrapper at [service.go:85-87](../../server/services/chat/service.go#L85) that exists to satisfy a `MessageNotifier` interface used by callers outside the chat package. Added a one-line task confirming the wrapper inherits the fix automatically (no code change there). Without this note, a reviewer might flag the wrapper as a missed entry point.

4. **Unbounded `QueryByField` flagged but not in-scope.** Per [CLAUDE.md](../../CLAUDE.md) §"SQL Efficiency" rule 3, every unbounded query is a memory-exhaustion risk. `GetCommunityMemberIDs` calls `QueryByField` with no LIMIT — a 5,000-member community returns 5,000 rows in one shot. Added a Phase 1 task that explicitly: (a) acknowledges this as pre-existing footprint shared with the community-event dispatcher (so we're not introducing it), (b) explains why naive LIMIT would silently under-deliver, (c) files a follow-up to add a paginated `IterateCommunityMembers(ctx, communityID, batchSize, fn)` that both dispatchers can consume. This documents the tradeoff in writing rather than leaving it as ambient debt.

5. **Field-naming sourced to the standard table.** Original log line used `recipient_count` without justifying the field name. Added a note that this is a custom field allowed under [docs/server/observability.md](../../docs/server/observability.md) §"Standard Field Names" "Entity-specific fields follow patterns" — and that `community_id`, `conversation_id`, `message_id` come from the standard table.

**No changes needed:**

- **Service-independence rule.** Per [docs/server/architecture.md](../../docs/server/architecture.md) §"Service Independence", services should depend on shared libraries, not other services. This fix has the chat **service** (`server/services/chat`) depend on the community **library** (`server/community`) — exactly the migration target the architecture doc recommends. No service-to-service injection introduced.
- **Sensitive-data masking.** No emails, tokens, or other sensitive fields appear in the new log lines. Recipient user IDs and counts are non-sensitive per the masking rules in [docs/server/observability.md](../../docs/server/observability.md) §"Standard Field Names" (which lists `user_id` as a non-masked standard field).
- **Connect error wrapping.** Per [CLAUDE.md](../../CLAUDE.md), public errors should use `connecterr.Internal(ctx, op, err)`. This fix is in an async dispatch goroutine spawned via `GoSafe` — errors can't reach the wire — so no `connecterr` usage is required. The plan correctly relies on log-emit + alerting instead.
- **Test infrastructure.** Plan uses `storage.SetupTestStorage(t)` and the existing `mockNotificationService` from `notifications_test.go` — both standard per [CLAUDE.md](../../CLAUDE.md) §"Server Testing" and [docs/server/architecture.md](../../docs/server/architecture.md) §"Testing Strategy". No `//go:build integration` tag needed (no AI calls; no external services).
- **Proto field conventions.** No proto changes. The plan correctly notes "No proto / RPC changes" — the fix is dispatcher-side only and doesn't touch `ChatConversation`, `ChatMessagePayload`, or any other wire type.
- **Comment style.** Plan's reference to "Function comment updated to start with the symbol name per `revive.exported`" is correct — exporting `getCommunityMemberIDs` → `GetCommunityMemberIDs` triggers the doc-comment requirement, and the plan calls that out.
- **Fan-out scale and throttling.** Already addressed in Open Questions with explicit recommendations to defer optimization until production data shows the need. Both questions cite the precedent of the community-event dispatcher operating at the same scale.
- **Client-side concerns.** Confirmed by inspection that `ChatMessagePayload` deep-link handling on the Flutter side (the `community_chat_pane.dart` path) is identical for community-wide and topic-scoped conversations. No client work in scope.
