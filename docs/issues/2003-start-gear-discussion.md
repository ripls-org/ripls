## Problem Statement

The reporter is the owner of a recently shared gear item that no borrower has yet expressed interest in. From their own gear detail page they cannot find a way to start a discussion / send a message. The maintainer who triaged the report (maintainer) confirmed the same: "It's not clear how to start the discussion, although I think if someone expressed interest, it would start."

The chat tab on the gear content view is gated on a non-empty `gear.conversation_id` ([app/lib/presentation/screens/gear/gear_content_view.dart:502-506](../../app/lib/presentation/screens/gear/gear_content_view.dart#L502-L506)). When the gear has no conversation, the user sees `ConversationPaneEmptyState` ([app/lib/presentation/widgets/content/content_shared_widgets.dart:65-82](../../app/lib/presentation/widgets/content/content_shared_widgets.dart#L65-L82)) — a centered, dimmed "No conversation yet" line with **no input, no CTA, and no way out**. The owner is stuck looking at a dead-end tab.

There is a deeper question of why the conversation is missing in the first place. `ShareGear` is supposed to create the conversation eagerly the first time the gear is shared with availability `FOR_LOAN` or `FOR_GIVEAWAY` and stamp the id onto `Gear.ConversationId` ([server/services/community/gear_sharing.go:256-290](../../server/services/community/gear_sharing.go#L256-L290)). So in the steady state every shared gear should already have a conversation by the time the chat tab is opened. The fact that this user does not suggests one of: (a) a stale client cache, (b) a gear that was created but never shared (the chat tab still renders), (c) a gear whose share path raced or partially failed, or (d) legacy gear that pre-dates the share-creates-conversation feature. We do not have the gear id from the feedback record so we cannot distinguish these without instrumentation — but the user-visible fix is the same in every case: the chat tab must always offer the owner a path to start the conversation, not just present a dead-end string.

This is a usability bug masquerading as a missing-feature bug: the server already supports gear conversations, the client already supports rendering them — the gap is a "create-and-open" entry point for the case where `conversation_id` is empty when the chat tab is opened.

## Codebase Findings

Concrete code locations behind the gap, summarized from the investigation:

- **Empty state with no CTA.** `_buildChatPane` ([app/lib/presentation/screens/gear/gear_content_view.dart:502-526](../../app/lib/presentation/screens/gear/gear_content_view.dart#L502-L526)) returns `const ConversationPaneEmptyState()` when `gear.conversationId.isEmpty`. `ConversationPaneEmptyState` ([app/lib/presentation/widgets/content/content_shared_widgets.dart:65-82](../../app/lib/presentation/widgets/content/content_shared_widgets.dart#L65-L82)) is a single `Center(child: Text(...))` — no tap target, no callback, no semantics for "tap to start." The widget is shared with experience, request, and community chat panes (see imports), so any change to it needs to make sense in all four contexts. Note: requests and experiences are two of the four canonical item types (giveaway, loan, request, experience) and get a conversation created with themselves as the topic at item-creation time — the empty state there is a purely defensive fallback and would not appear in normal operation. Gear is not one of these four types, which is why the empty-state gap exists specifically here.
- **Server `StartConversation` rejects gear topics.** The handler at [server/services/chat/conversations.go:164-246](../../server/services/chat/conversations.go#L164-L246) only switches on `TransferId` and `RequestId`; the `default` branch returns `CodeInvalidArgument` ("topic is required") for everything else — including `gear_id`. The Flutter app would not be able to call `StartConversation` with a gear topic today even if the wiring existed on the client.
- **The chat library already supports gear conversations.** `chat.CreateOrGetConversation` at [server/chat/conversations.go:90-194](../../server/chat/conversations.go#L90-L194) has a `*models.ConversationTopic_GearId` branch (lines 140-146) that fetches the gear, returns an empty initial-participant list, and is idempotent across the `(community_id, gear_id)` key. So the only missing piece on the server is exposing this through `StartConversation` with the right authorization check.
- **Authorization model for gear conversations is well-defined.** Gear conversations are scoped per `(community_id, gear_id)`. Participants are added lazily — `GetConversation` already calls `addUserAsParticipant` for `topic.GetGearId() != ""` ([server/services/chat/conversations.go:302-309](../../server/services/chat/conversations.go#L302-L309)) when a community member opens the chat. The same membership rule should govern `StartConversation`: caller must be a member of an active community the gear is shared with, OR the gear's owner.
- **Server creates the gear conversation only on `ShareGear` with availability `FOR_LOAN` or `FOR_GIVEAWAY`.** [server/services/community/gear_sharing.go:256-290](../../server/services/community/gear_sharing.go#L256-L290). Persists the id on `Gear.ConversationId` (line 273). Also emits a `LOAN_SHARED` / `GIVEAWAY_SHARED` system message anchor (lines 296-309). Gear that exists but is not shared in any community has no conversation id by design.
- **`Gear.ConversationId` is the canonical source.** `populateCommunityFields` reads from `Gear.ConversationId` first ([server/services/gear/service.go:466](../../server/services/gear/service.go#L466)) and falls back to `CommunityGear.ConversationId` for pre-migration records (lines 481-484). The conversation id is gear-scoped, not community-scoped — once created, it travels with the gear across all communities it is shared with.
- **Flutter never calls `StartConversation` today.** `grep -r startConversation app/lib/` returns only generated bindings; no hand-written caller. There is no existing repository or service method to wire to.
- **Chat composer renders only when a conversation id is present.** `InlineConversationView` at [app/lib/presentation/widgets/content/inline_conversation_view.dart:300-336](../../app/lib/presentation/widgets/content/inline_conversation_view.dart#L300-L336) is constructed with a required `conversationId` and renders the pill input ([line 456+](../../app/lib/presentation/widgets/content/inline_conversation_view.dart#L456)) unconditionally — there is no "before first conversation" pre-state. So any fix that wants the owner to type *before* a server-side conversation exists has to either eagerly create the conversation on entry or render a custom pre-create CTA.

## Potential Solutions

### Option A: Auto-create the gear conversation on first chat-tab open

**Approach:** When the chat tab is opened (or the gear loads) and `gear.conversationId` is empty, transparently call a server endpoint that creates/returns the gear conversation, stamp the id on the in-memory `Gear`, and re-render the chat pane with `InlineConversationView` exactly as if the conversation had been there all along. The user perceives zero friction — they tap the tab, the composer is there, they type.

Server side: extend `StartConversation` to accept `gear_id` topics. Authorization: the caller must (a) own the gear, or (b) be an active member of at least one community the gear is shared with (`CommunityGear` join). Fetch the gear, validate, then delegate to `chat.CreateOrGetConversation` with the request's `community_id` and a `ConversationTopic_GearId` topic. Persist `conversation_id` back onto the `Gear` row inside the same call so the next `GetGear` returns it directly. (`CreateOrGetConversation` is already idempotent, so this is safe even if `ShareGear` later runs.)

Client side: add `ChatRepository.startGearConversation(gearId, communityId)` that calls the new RPC and returns the conversation id. In `_buildChatPane`, if `gear.conversationId` is empty, fire the start call on tab entry and show a small inline spinner placeholder (not the dead-end text) until the id resolves; then swap in `InlineConversationView`. Cache the result locally; on success, also call `gearRepository.invalidate(gearId)` so the next read sees the canonical id.

- **Pros:** Single, atomic UX — the user never sees an empty state at all. Symmetric with how community-wide conversations already work (`GetConversationForCommunity` creates if missing, [chat_service.proto:541](../../proto/ripls/api/chat_service.proto#L541)). Removes the entire class of "dead chat tab" bugs regardless of which root cause (no share, race, legacy gear) put us there. Reuses existing idempotent server primitive.
- **Cons:** Conversation rows get created speculatively, including for gear the owner only browses past on their own profile without intending to start a discussion — modest write amplification (one ChatConversation row per gear × per community that the chat tab is opened in). Also implicitly answers the "should the owner be able to start a discussion before any share has happened" question with "yes, if they have a `community_id` context" — which may or may not be the intended product posture.
- **Effort:** Medium. Server: ~40-60 LoC + tests for the new `StartConversation` gear branch (authorization, gear-fetch, conversation_id persistence). Client: ~30 LoC for the repository method + ~20 LoC for the empty-state replacement + viewmodel plumbing. No proto change required (`StartConversationRequest.topic` already supports `gear_id`).

### Option B: Show an explicit "Start Discussion" CTA in the empty state

**Approach:** Replace `ConversationPaneEmptyState` for the gear case with a tappable card that says something like "Be the first to start a discussion about this gear" with a Start button. The tap calls the same server endpoint as Option A, then swaps in the live chat view.

- **Pros:** No surprise — the action is explicit, the moment of conversation creation is user-initiated, and the user has a clear understanding of "I am starting something." Easier to A/B test or revert. Also doesn't pre-allocate conversations for users who just bounce through the chat tab.
- **Cons:** One extra tap. The empty-state widget is shared with experience, request, and community panes — though adding a topic-aware variant would only be needed for gear, since experiences and requests always have their own conversations as the topic and would not hit this empty-state path in normal operation. Doesn't change the *root* of "why does ShareGear sometimes not produce a conversation" — if that has a bug, this fix masks it instead of fixing it.
- **Effort:** Small-medium. Server: same as Option A. Client: ~50 LoC for the new CTA empty state, plus the four existing call sites of `ConversationPaneEmptyState` to confirm they don't regress.

### Option C: Investigate and fix the *real* root cause for missing `conversation_id`

**Approach:** Treat the empty `conversation_id` as a bug. Instrument production (e.g., log when `GetGear` returns an empty `conversation_id` for an owner whose gear is shared anywhere); confirm whether ShareGear is firing reliably for newly-created gear; if there's a race or a missed call, fix it. Backfill conversation ids for any historical gear that was shared before the perpetual-gear-chat feature shipped.

- **Pros:** Removes the underlying defect rather than papering over it. Future gear / users benefit automatically.
- **Cons:** Doesn't actually solve the *user-visible* problem on its own — even with 100% of new shares producing a conversation, the UI still shows an empty-state dead end for the (probably non-trivial) backfill window. And the user's wording suggests a fresh share, so the bug may be subtle or environment-specific; full root-cause work could take many cycles, while the user-facing pain is fixable now.
- **Effort:** Unknown — depends on whether there's actually a deterministic bug. Backfill alone is medium (migration to compute conversation ids for legacy shared gear).

## Recommendation

**Option A (auto-create on first chat-tab open), with a small piece of Option C tacked on as a follow-up observation gate.**

Why over Option B (explicit CTA): the empty state we have today is itself the bug — it's a *silent* dead end. Replacing one dead end with a button is a fix, but auto-creating is materially better UX because the user never has to learn that gear chats have a "start" affordance distinct from "type to begin." The same UX is already used for community chats via `GetConversationForCommunity` (the chat service literally has a comment saying "Creates the conversation if one does not yet exist") — gear chats should mirror it. The "modest write amplification" cost is small in absolute terms: gear conversations are cheap rows, idempotent on `(community_id, gear_id, topic)`, and the chat tab is not a heavily-trafficked surface for non-owners-who-don't-care.

Why over Option C (root cause): we should still understand why `Gear.ConversationId` was empty for this reporter (Open Question), but that investigation is a follow-up, not a blocker — Option A makes the symptom go away for every user immediately whether or not we ever explain the original gap.

The piece of Option C we *do* want now: a server-side `Warn` log when `StartConversation` is called with a `gear_id` whose target `Gear.ConversationId` is already non-empty but the in-memory `GetGear` response was stale, or when it is called for gear that is not shared with any community. Both are diagnostic — they will tell us, after we ship, whether the missing conversation came from a sharing race vs. an unshared-gear chat-tab open vs. legacy backfill.

## Open Questions

- **Should we allow chat tab use on gear that is not shared with any community?** — *Recommendation: no, at least not in this fix.* The whole point of a gear conversation is to discuss the gear *with a community*. If the gear has no `CommunityGear` row, there is no community context for a conversation; tapping the chat tab in that state should continue to show an empty state (with copy that explains "Share this in a community to start a discussion" and an inline link to the share sheet). Option A's auto-create only fires when there is a `community_id` in scope. Owner-only / private chat is out of scope for this issue.
- **What `community_id` do we pass when the gear is shared into multiple communities?** — *Recommendation: the client's current `selectedCommunity.id` if the gear is shared there; otherwise the first community in `gear.sharedCommunities` that the current user is a member of.* The conversation id itself is gear-scoped (one perpetual chat per gear regardless of how many communities it's shared with — confirmed by `Gear.ConversationId` being the canonical store and `CreateOrGetConversation`'s idempotency key including `community_id` only as a tie-breaker), so the choice mainly determines which community the system message anchors point to. We already make the same decision in the existing ShareGear path; the auto-create call should mirror that policy.
- **Should `StartConversation` for `gear_id` also emit the `LOAN_SHARED` / `GIVEAWAY_SHARED` anchor system message when it creates the conversation?** — *Recommendation: no.* That anchor is conceptually owned by the `ShareGear` flow ("the owner made this gear available"), not by the chat-tab-opening flow. Auto-create-on-chat-open is a backfill / recovery path for the case where the share-time creation didn't happen. The anchor should be re-emitted only inside `ShareGear`, which it already is, and only on the first share. If we discover a real production case where the conversation got created without an anchor we can revisit, but emitting on every `StartConversation` would re-create the dedup bug #1679 fixed.
- **Does the owner need a different UX from a non-owner community member for the empty-state-during-create flash?** — *Recommendation: no.* Both are valid participants in a gear chat. The inline spinner placeholder during the brief `StartConversation` round-trip is identical regardless of role.
- **Do we need to gate this on a feature flag?** — *Recommendation: no.* The change is small, the server side is additive (`StartConversation` already exists; we're widening one switch), and there is no realistic rollback story for "users see the empty state again" that beats "just fix forward." If we want pre-launch reassurance, run the integration tests on a preview deployment.
- **Do we have an obvious follow-up for the *original* missing-`conversation_id` puzzle?** — *Recommendation: file a separate issue once we have the diagnostic logs from this fix in production.* The logs added in Phase 1 (gear share-state on `StartConversation` for `gear_id`) will give us a first observation of how often we hit each bucket (unshared gear, stale GetGear, legacy backfill). One week of data is enough to decide whether a backfill migration is needed.

## Implementation Plan

### Phase 1: Server-side `StartConversation` gains a `gear_id` branch

**Goal:** A correctly-authorized client can call `StartConversation` with `topic = { gear_id }` and get back either a freshly created or pre-existing gear conversation id, with the id persisted on the `Gear` row so the next `GetGear` returns it.

**Tasks:**
- [ ] **Add the `gear_id` case to `StartConversation`'s topic switch.** In [server/services/chat/conversations.go:196-228](../../server/services/chat/conversations.go#L196-L228), insert a `case *api.ConversationTopic_GearId:` branch before `default`. Inside the branch: (a) fetch the gear via `s.storage.GetByID(ctx, topic.GearId, gear)` and return `CodeNotFound` if missing; (b) if `gear.OwnerId == authInfo.UserID`, allow; otherwise verify the caller is an active member of *some* community the gear is shared with by querying `CommunityGear` for the gear and intersecting with the caller's community memberships — reject with `CodePermissionDenied` if no overlap. Also require the gear to be shared with at least one community (any `CommunityGear` row) — return `CodeFailedPrecondition` with copy along the lines of "this gear must be shared with a community before a discussion can start" if not.
- [ ] **Confirm the request's `community_id` is a community the gear is actually shared with** (not just any community the caller is in). This is already implicitly guaranteed for transfer/request topics via the entity lookup; for gear, add an explicit check that there is a `CommunityGear` row for `(req.Msg.CommunityId, topic.GearId)`. Reject with `CodeFailedPrecondition` otherwise so the client can fall back to a different community.
- [ ] **Persist `conversation_id` back onto `Gear`.** After the `chat.CreateOrGetConversation` call returns, if `gear.ConversationId == ""`, write it on the gear row inside the same RPC. This closes the recovery loop: future `GetGear` calls return the id from the canonical column without a second `StartConversation` round-trip. Use `s.storage.Update(ctx, gear)`. Add the owner to the participant list via `chat.AddParticipantToConversation` only if they are not already present (this matches the policy in `createGearConversation` at [server/services/community/gear_sharing.go:503-517](../../server/services/community/gear_sharing.go#L503-L517)).
- [ ] **Don't emit a system-message anchor here.** The `LOAN_SHARED` / `GIVEAWAY_SHARED` anchor is conceptually owned by `ShareGear`; re-emitting from `StartConversation` would re-introduce the dedup pain `#1679` fixed.
- [ ] **Add a `Warn` log when `StartConversation` for `gear_id` creates a conversation for a gear whose `ShareGear`-time creation evidently didn't fire** (`gear.ConversationId == "" && len(communityGears) > 0`). Use the standard logging shape per [docs/server/observability.md §Standard Field Names](../server/observability.md#standard-field-names): obtain a context logger via `logging.LoggerWithContext(ctx)`, attach `"operation":"StartConversation"`, `"gear_id":...`, `"community_id":...`, `"topic_type":"gear"`, and emit a single `Warn` line with a stable, greppable message like `"backfilling gear conversation at chat open"`. **Do not invent a non-standard `diagnostic` field — message-based filtering with the standard entity fields is sufficient and matches the alert/digest pipeline's expectations.** **[audit:observability]** The `rpc_errors_{environment}` log-based metric (Part 4 of `observability.md`) groups by `operation`, so the existing alerting picks this up automatically without a new metric. This is the observation gate from the Recommendation — it tells us, after we ship, whether the original bug is a real ongoing leak or a one-time legacy backfill issue.
- [ ] **Error codes follow [CLAUDE.md §Error Handling](../../CLAUDE.md).** All non-internal errors in the new branch use `connect.NewError(...)` directly (e.g. `CodeNotFound`, `CodePermissionDenied`, `CodeFailedPrecondition`). `connecterr.Internal(ctx, "StartConversation", err, kv...)` is reserved for genuine internal failures (storage write failures, marshaling errors) — never use it for user-input validation. **[audit:server-architecture]**
- [ ] **Unit tests.** Add to [server/services/chat/conversations_test.go](../../server/services/chat/conversations_test.go):
  - `TestStartConversation_GearTopic_OwnerSucceeds` — owner of a gear shared with a community; assert returned `conversation_id` is non-empty and equals `gear.ConversationId` on a subsequent `GetByID`.
  - `TestStartConversation_GearTopic_CommunityMemberSucceeds` — non-owner who is a member of one of the gear's shared communities; same assertions, plus assert the caller appears in the conversation's participant list.
  - `TestStartConversation_GearTopic_NonMemberDenied` — caller is in no overlapping community; assert `CodePermissionDenied`.
  - `TestStartConversation_GearTopic_UnsharedGear` — gear exists but has no `CommunityGear` rows; assert `CodeFailedPrecondition`.
  - `TestStartConversation_GearTopic_Idempotent` — call twice in a row; second call returns same id, no new conversation row created.
  - `TestStartConversation_GearTopic_BackfillLogged` — gear with non-empty `CommunityGear` set but empty `gear.ConversationId`; assert the diagnostic log line is emitted at Warn (use a `slog` handler capture).
- [ ] **Authorization regression test.** `TestStartConversation_GearTopic_RequiresCommunityIdInShareSet` — request specifies a `community_id` the caller is in but that the gear is *not* shared with; assert `CodeFailedPrecondition`. This locks in that the request's `community_id` must match the share set.
- [ ] **Build verification.** `npm run build` and `go test ./server/... -count=1 -timeout 5m`. Per CLAUDE.md §Go Server Build Verification, also run `go build -tags=integration ./...` since `StartConversation` is consumed by integration tests in `server/services/chat/streaming_test.go` and friends.

**Validates:** The server contract is correct in isolation, can be unit-tested without the Flutter app, and the diagnostic logging hook is in place. Any client wiring built on top in Phase 2 has a stable backend.

### Phase 2: Client auto-creates the conversation when the chat tab is opened with an empty `conversation_id`

**Goal:** When the user opens the chat tab on a gear they have permission to chat about (owner or member of one of its communities), they never see a dead-end empty state — either the live `InlineConversationView` is up immediately, or a transient spinner shows for at most one network round-trip before the live view appears.

**Tasks:**
- [ ] **Add `ChatRepository.startGearConversation`** to [app/lib/data/repositories/chat_repository.dart](../../app/lib/data/repositories/chat_repository.dart) (the file exists today; the method is new). Signature: `Future<String> startGearConversation({required String gearId, required String communityId})`. Call `_service.startConversation(...)` with `topic = ConversationTopic(gearId: gearId)` and the supplied `communityId`. Return `response.conversationId`. **No caching on the call itself** — this is a one-shot recovery RPC, not a fetch.
- [ ] **Cache-invalidation policy for the new method — read carefully.** `ChatRepository` deliberately **does not** trigger `contentCacheInvalidationProvider` for ordinary mutations like `sendMessage` and `markMessagesRead` (see the constructor comment at [chat_repository.dart:23-28](../../app/lib/data/repositories/chat_repository.dart#L23-L28): firing it caused parent content views to reload, disposing the autoDispose `conversationProvider` and re-fetching messages with a visible flicker). `startGearConversation` is **categorically different** — it changes the gear's `conversation_id` field, which the parent `GearContentView` reads directly, so the parent **must** reload to pick up the new id. Resolution: the **viewmodel** (not the repository) handles the post-call refresh by calling `gearRepository.invalidate(gearId, communityId: state.communityId)` followed by `loadGearDetails(communityId: state.communityId)`. The repository stays narrow — service call + namespace cache clear (`_cache.clear(pattern: '$_namespace:conversation:*')` for defensiveness) — and does not touch `contentCacheInvalidationProvider`. **[audit:caching]** This preserves the flicker-prevention invariant from the existing chat-repo design while still propagating the new conversation_id to the screen. Document this asymmetry in a short `///` comment on the new method.
- [ ] **Replace the empty state in `_buildChatPane`.** In [app/lib/presentation/screens/gear/gear_content_view.dart:502-526](../../app/lib/presentation/screens/gear/gear_content_view.dart#L502-L526), if `gear.conversationId.isEmpty`, kick off a one-shot `ensureGearConversation()` call inside the chat-tab activation path (guarded by an in-flight flag on the viewmodel — see next task) and render a small loading placeholder instead of `ConversationPaneEmptyState`. The placeholder must be **accessibility-correct per [docs/client/accessibility.md](../client/accessibility.md)**: wrap the visible loading text in a `LiveRegion(child: ...)` so screen readers announce "Starting discussion…" on entry; use `context.l10n.gearChatStartingDiscussion` for the visible string (not a raw literal — the `require_l10n_for_semantic_labels` lint rule rejects raw literals on any semantics-visible string). Do **not** use a `GestureDetector` or raw `InkWell` anywhere new in this pane; if a retry button is rendered on the error path it must be a `Tappable` from `app/lib/presentation/widgets/accessibility/` with a `semanticsLabel: context.l10n.a11yGearChatRetryStart`. **[audit:a11y]**
- [ ] **Viewmodel plumbing.** Add `Future<void> ensureGearConversation()` to [app/lib/presentation/viewmodels/gear_view_model.dart](../../app/lib/presentation/viewmodels/gear_view_model.dart). Idempotent (no-op if `state.gearDetails?.conversationId` is already non-empty; no-op if a create is already in flight — track `bool _conversationCreateInFlight` as a private field on the notifier, not on `state`). After the awaited `chatRepository.startGearConversation(...)`, perform `if (!ref.mounted) return;` before any state assignment, per [docs/client/architecture.md §Async Safety in Notifiers](../client/architecture.md#async-safety-in-notifiers). The viewmodel itself owns the refresh side: on success, call `await gearRepository.invalidate(gearId, communityId: state.communityId)` followed by `await loadGearDetails(communityId: state.communityId)` (the existing method on this notifier) to pull the canonical `conversation_id` back in. Add another `if (!ref.mounted) return;` between the two `await`s. On failure, classify via `RpcErrorHandler.classify(e)` per [app/lib/core/errors/README.md](../../app/lib/core/errors/README.md) and stamp `state.error` so the widget can render an inline retry button via `RpcErrorHandler.localize(state.error!, context.l10n)`. Decide which `community_id` to pass per the second Open Question above (selected community if the gear is shared there; otherwise first shared community the user is a member of, sourced from `state.sharedCommunities` and `gear.sharedCommunities`). If there is no such community, do not call the RPC — short-circuit to the unshared-gear path (next task). **[audit:client-architecture]**
- [ ] **New unshared-gear empty state.** When `gear.conversationId.isEmpty` *and* the gear is not shared with any community the user belongs to, render a `GearChatUnsharedEmptyState` (new widget) explaining the precondition. - **[audit:server-architecture]** — Phase 1 now explicitly bans `connecterr.Internal(...)` for user-input validation in the new `gear_id` branch; only genuine internal failures use it. This matches CLAUDE.md §Error Handling and the existing patterns at [server/services/chat/conversations.go](../../server/services/chat/conversations.go).

Dropped the non-standard `diagnostic` field that didn't match any existing log shape; the `rpc_errors_{environment}` log-based metric already groups by `operation` so no new metric is needed.
- **[audit:client-architecture]** — Phase 2's viewmodel task now explicitly requires `if (!ref.mounted) return;` guards after every async await per [docs/client/architecture.md §Async Safety in Notifiers](../client/architecture.md#async-safety-in-notifiers), uses a private `_conversationCreateInFlight` field (not state) for the in-flight guard, and routes errors through `RpcErrorHandler.classify` / `localize` per the canonical viewmodel-error contract in [app/lib/core/errors/README.md](../../app/lib/core/errors/README.md). Verified MVVM layering: viewmodel calls repository, repository calls service, widget calls viewmodel — no shortcuts.
- **[audit:caching]** — Original draft called for the chat repository to fire `contentCacheInvalidationProvider.notify()` after the new RPC. Reviewing the existing `ChatRepository` constructor comment at [chat_repository.dart:23-28](../../app/lib/data/repositories/chat_repository.dart#L23-L28) revealed that pattern was **intentionally removed** to prevent a parent-content-view refresh flicker that disposes `conversationProvider`. Plan now explicitly preserves that invariant — the viewmodel (not the repository) owns the post-call refresh because `startGearConversation` is the one mutation that actually changes a parent-view-observed field. Repository stays narrow: service call + local namespace cache clear.
- **[audit:i18n]** — Replaced "`flutter gen-l10n`" with "`npm run generate`" per [docs/client/i18n.md](../client/i18n.md) and CLAUDE.md (npm scripts are the canonical entry point). Added explicit list of new ARB keys with the `a11y*` prefix split out for accessibility labels. Both `app_en.arb` and `app_es.arb` must be updated before regen because `nullable-getter: false` fails the build on missing keys.
- **[audit:a11y]** — Loading placeholder now requires `LiveRegion` per [docs/client/accessibility.md](../client/accessibility.md) so screen readers announce "Starting discussion". All new tap targets must use `Tappable` (not `GestureDetector` / `InkWell`) and the share-sheet open must use `showAccessibleModal` (the `prefer_accessible_modal` lint rejects raw `showModalBottomSheet` outside the dedicated helper). Phase 2 now requires running `node scripts/check_a11y.js` and confirming the allowlist stays flat-or-shrinking. Phase 3 adds a VoiceOver / TalkBack pass against the new state.
- **[audit:testing]** — Phase 2 test tasks now name the canonical test-helper paths (`app/test/helpers/l10n_helpers.dart`), call out `@GenerateMocks` + `build_runner build`, and apply the `addTearDown(() => container.dispose())` + `reset(mock)` cleanup pattern from [docs/client/testing.md](../client/testing.md). Viewmodel test is primary; widget test is secondary smoke.

No findings required structural changes to the recommendation, phasing, or open questions. The recommendation (Option A: auto-create on first chat-tab open) remains the right call against all six audit lenses.
