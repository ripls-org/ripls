## Problem Statement

The "known for" chips — Hiking, Power Tools, Cooking, etc. — currently render as inert labels on both surfaces that show them: the workshop screen (community / "Everything" aggregate) and the user-profile screen (per-user). The chip text tells the viewer *what* a scope is known for, but offers no way to drill in: which specific gear / experiences / requests power that label, and which members contributed them.

The issue asks for a tappable chip that pushes a detail screen answering both halves, **from either surface**:

1. **What** — representative items in the active scope whose category matches the tapped chip (gear listings, experiences, requests), with completed/fulfilled items emphasized.
2. **Who** — the people behind those items. On the workshop surface that's the community members who contributed; on the user-profile surface it's the people the target has shared with for that category (loan borrowers, experience attendees, request fulfillers).

The detail screen must follow the visual + interaction pattern of the existing time / money / CO₂ impact-row detail screens so both tabs keep a single navigation language: a viewer tapping any signal on a home-style screen lands somewhere structurally familiar.

The overflow menu in the detail screen's app bar lets the target (the self-viewing user, or any viewer on the community surface) **hide** the skill or **permanently delete** it, so it is never recreated from the underlying data for that user / community.

## Potential Solutions

### Option A: New RPC + new detail screen mirroring the impact-row screens
- **Approach:** Add a `GetCategoryDetail` RPC that mirrors the existing `known_for.Derive` signature — same `Mode` (`ModePerUser` / `ModePerCommunity`), same `OwnerID`, same `CommunityIDs`, plus a `Category` filter. Returns a small set of representative items (gear / experiences / requests in scope whose category matches) plus the de-duplicated list of member IDs behind them. The RPC lives on `WorkshopService` (both surfaces call into it — the user-profile screen already routes through workshop-style aggregation patterns; one RPC is simpler than mirroring on `ProfileService`). Build one `KnownForCategoryDetailScreen` that takes the same `Mode`/`OwnerID`/`CommunityIDs`/`Category` quadruple. Shaped like the time / money / CO₂ screens: app bar with an overflow menu (Phase 4), swipe-to-close, `CustomScrollView` body, "Where it shows up" item section, "Who shows up" member section, "Keep the momentum" lean-card tail. Make `KnownForChips` carry an `onTap(String tag)` callback; the workshop screen wires it with `ModePerCommunity` + the carousel's community-id snapshot, and the user-profile screen wires it with `ModePerUser` + the viewer's shared-community set (or the target's active community set for self-view, mirroring the `#1996` rule).
- **Pros:** Server owns the data shape — the client never re-derives categories or aggregates per-source. Mirrors the existing detail-screen pattern exactly, so reviewers and future contributors don't need to learn a new convention. Reuses every shared widget (`RecentItemsList`, `_MemberRow`-style avatar rows, `SwipeToCloseMixin`, `NavigationHelpers.pushScreen`). Server-side scoping keeps the chip query and the detail query in lock-step — they read the same tables. One screen + one RPC handles both surfaces (no parallel `WorkshopKnownForCategoryDetailScreen` / `ProfileKnownForCategoryDetailScreen`).
- **Cons:** A new RPC + proto round-trip. The `known_for` library currently returns only tag strings, so the detail-data query is new work even though the source tables are the same.
- **Effort:** Medium.

### Option B: Client-side derivation off the existing brief payload
- **Approach:** Stash the per-source contribution lists on `BriefPayload` (gear ids, experience ids, request ids per category) so the chip-detail screen can render entirely from the brief response without a follow-up RPC.
- **Pros:** Zero new RPCs. Detail open is instant — data is already in memory.
- **Cons:** Bloats the brief response with data 99% of viewers never see — they have to tap a specific chip to surface it. The brief is fetched on every workshop open and is cached client-side; growing it for a low-frequency drill-down trades server work for bigger payloads on every load. Couples the brief proto to the detail screen's data needs, making future iteration harder.
- **Effort:** Small on the client, medium on the proto + server (need new repeated fields, ID hygiene, careful payload-size budgeting).

### Option C: Client routes through existing list screens, no detail screen
- **Approach:** Tapping a chip pushes the existing community-public screen filtered to the tapped category, or the discover/feed screen with a category filter applied.
- **Pros:** No new screen at all. Reuses surfaces that already exist.
- **Cons:** Loses the editorial framing the issue asks for ("match the design of the metrics detail screens"). The existing community screens aren't built around a single category; filtering them produces a generic list, not the structured "What + Who" layout the issue describes. The whole point of design parity with the impact-row screens is that the workshop has a consistent drill-down vocabulary; routing to a different surface breaks that.
- **Effort:** Small but doesn't satisfy the brief.

## Recommendation

**Option A.** It's the only path that satisfies the issue's design-parity requirement — every workshop home-screen tap (impact row, postcard, chip) lands on a structurally similar detail surface. The new RPC is a thin slice over the same gear / experience / request tables the chip derivation already reads, so the server-side work is straightforward (and naturally lives next to or inside the `known_for` package as a per-category detail variant).

The only meaningful tradeoff is shipping a new RPC. Option B would avoid that at the cost of inflating the brief payload for data the viewer rarely opens; on a hot path (the brief is fetched every time the workshop tab opens), that's the wrong tradeoff. Option C sidesteps the issue's design intent.

## Resolved Decisions

Resolved 2026-05-18 (user direction). Locked in for v1; revisit only if a concrete need surfaces.

- **What "representative" means for the items section.** Show the **ten most recent items** that fit the category, ranked by recency (newest first). No completion-bonus reweighting, no "+1 if fulfilled" weighting — just recency. Items are capped at 10 server-side. No "Show more" affordance in v1.
- **Member section.** Name + avatar only — no per-person stats. Tap routes to `UserScreen(userId: ...)` via `NavigationHelpers.pushScreen`.
- **Chip tap on the user-profile surface.** In scope for v1 — both surfaces ship together via a single shared `KnownForCategoryDetailScreen` that takes `Mode` / `OwnerID` / `CommunityIDs` / `Category` and routes to the same `GetCategoryDetail` RPC. On user-profile surface the community-ID set is the viewer ↔ target shared-community intersection (or the target's full active set when `state.isSelfView` is true, mirroring the `#1996` self-view rule).
- **Who can hide / permanently delete a known-for skill.** User-profile surface: only the target user themselves (gate the overflow menu on `state.isSelfView`). Workshop surface: any member of the active community. Revisit only if abuse surfaces.
- **Hide vs. permanently delete semantics.** **Hide** writes a `suppressed_known_for` row with `permanent = false` (a future "Unhide" UI, out of scope here, can clear it); `ClassificationServerSnackbar` with an `UndoHideKnownForCategory` RPC. **Permanently delete** writes the same row with `permanent = true`; `ClassificationIrreversible` with a confirmation dialog at action time. Both prevent chip recreation.
- **Empty-state vs. suppressed-state framing.** A category whose underlying rows disappeared between brief and detail renders the editorial header + "These items aren't around anymore" copy. A category that was hidden / permanently deleted (server returns `suppressed == true`) renders "This skill has been removed" — distinct from the empty state.
- **Pull-to-refresh.** Re-fetches the per-category detail RPC (matches the rest of the workshop's detail screens).
- **RPC naming + location.** `GetCategoryDetail` on `WorkshopService`. The shared `known_for` Go library produces the data either way; both surfaces call the same RPC.

## Implementation Plan

### Phase 1: Server-side per-category detail derivation

**Goal:** The server can answer "what items and who is behind this category in this scope" in a single round trip, for **both** the per-community (workshop) and per-user (profile) modes.

**Tasks:**
- [ ] Extend `server/known_for/` with a new `Detail(ctx, storage, opts)` function (in a new `detail.go`). Options carry the same `Mode` / `OwnerID` / `CommunityIDs` triple as `Derive`, plus a `Category string` filter (matched against the *normalized* category key, not the raw display string, so locale / case / whitespace differences don't drop legitimate matches). `Mode == ModePerUser` scopes items to those the `OwnerID` owns/hosts/requests; `Mode == ModePerCommunity` scopes items to the community set. Re-uses the existing `loadLoanInputs` / `loadScopedExperiences` / `loadScopedRequests` data paths — both modes are already wired in those helpers (see the `if opts.Mode == ModePerUser` branches at [`experiences.go:64`](../../server/known_for/experiences.go#L64), [`loans.go:70`](../../server/known_for/loans.go#L70), [`requests.go:63`](../../server/known_for/requests.go#L63)). Instead of summing into a category-counts map, `Detail` collects the actual `Gear` / `Experience` / `Request` entities whose category matches plus the user IDs touching them.
- [ ] **[audit]** Mirror the recently-fixed `community_*` pivot semantics — do NOT filter pivots on `Archived` (a completed experience or fulfilled request archives its pivot row as a side effect; archived items are exactly the rows we want to surface). Filter on entity state instead, with `EXPERIENCE_STATE_CANCELLED` and `REQUEST_STATE_CANCELLED` excluded. This is the same fix that's already live in `known_for/experiences.go` and `known_for/requests.go`.
- [ ] **Suppression filter.** Before ranking, exclude entities whose `(scope_kind, scope_id, category_key)` matches a row in the new `suppressed_known_for` table (introduced in Phase 4 — `Detail` will accept the filter even on Phase 1 by returning an empty list when no rows exist yet; the actual lookup is a no-op until Phase 4 lands). For `ModePerCommunity`, suppression rows are keyed by `(community_id, category_key)` for every community in `CommunityIDs`. For `ModePerUser`, suppression rows are keyed by `(user_id, category_key)` where `user_id == OwnerID`. If any matching suppression row exists, return an "this skill has been removed" sentinel in the response so the client can decide whether to navigate away or render an empty state.
- [ ] Output shape: an in-package struct carrying the **ten most recent items** in the category (newest first, no completion-bonus reweighting — pure recency ranking per the resolved decision) and a de-duplicated list of member IDs (cap configurable, default 24). The item entries are storage-layer values (`models.Gear` / `models.Experience` / `models.Request`); the service handler converts them to `EntityCardCore` on the wire. Recency is taken from the entity's most-recent meaningful activity timestamp (gear: `updated_at` if newer than `created_at` else `created_at`; experience: `scheduled_at` if present else `created_at`; request: `updated_at` else `created_at`) — pick the same per-entity recency field the chip-derivation already reads, so the two paths can't drift. On `ModePerUser`, the member-ID list contains the people the target has *shared with* in this category (loan borrowers, experience attendees, request fulfillers) — not the target themselves (their avatar is already in the surrounding profile screen).
- [ ] Add proto messages `GetCategoryDetailRequest` / `GetCategoryDetailResponse` to `proto/ripls/api/workshop_service.proto`. Request carries `Mode mode`, *optional* `string owner_id`, `repeated string community_ids`, `string category`. **[audit, revised post-#2012]** Response carries `repeated EntityCardCore items` from [`proto/ripls/api/entity_card.proto`](../../proto/ripls/api/entity_card.proto) — the unified entity-card shape landed in [#2012](https://github.com/Type2Fun-Foundation/ripls/issues/2012) (`context_id`, `EntityKind kind`, `title`, *optional* `subtitle`, *optional* `media_id`). The `EntityKind` enum supersedes `AvailableNowKind` and carries every value we need (`GEAR`, `EXPERIENCE`, `REQUEST`, `GIVEAWAY` — `TRANSFER` and `COMMUNITY` are inapplicable to this RPC). No surface-specific overlay is needed here (no `mini_label` / `subtitle` carries the "Completed / Upcoming / Asking" framing — set `subtitle` to the per-kind state phrase server-side). Response is `repeated EntityCardCore items` + `repeated string member_ids` + *optional* `bool suppressed` so the client can render the "this skill has been removed" empty state distinctly from "no items found". This **supersedes** the pre-#2012 plan that reused `AvailableNowItem`; the consolidation issue's recommendation was for new surfaces (this is one) to pick `EntityCardCore` directly.
- [ ] Wire a `GetCategoryDetail` RPC on the workshop service that calls `known_for.Detail`, converts each storage entity to an `EntityCardCore`, and serializes the result. Hardcode the `EntityKind` per source: gear rows → `ENTITY_KIND_GEAR` (or `ENTITY_KIND_GIVEAWAY` when the gear is in a giveaway terminal state — match the same discriminator the `available_now` aggregator uses); experiences → `ENTITY_KIND_EXPERIENCE`; requests → `ENTITY_KIND_REQUEST`. If a shared helper for "kind from storage entity" doesn't exist in [`server/entitycard/`](../../server/entitycard/), add one in that package as part of this work (e.g. `KindFromGear(gear models.Gear) api.EntityKind`); per [#2012](https://github.com/Type2Fun-Foundation/ripls/issues/2012)'s recommendation, every kind-discriminator decision routes through this helper package so the rules don't drift. **[audit]** Structured logging via `logging.LoggerWithContext(ctx)` with `operation="GetCategoryDetail"`, `mode`, `category`, *optional* `owner_id` (only when `ModePerUser`), `community_id_count`, `item_count`, `member_count` — per [docs/server/observability.md](../server/observability.md) §"Standard Field Names". `connecterr.Internal(ctx, op, err, kv...)` for any internal-error wrapping (per [docs/server/architecture.md](../server/architecture.md) §"Error wrapping"; the bare `connect.NewError(CodeInternal, err)` pattern is gated by CI).
- [ ] **[audit]** When logging a request-entity ID (the `models.Request` kind that surfaces in `items`), use the `target_request_id` log field — never `request_id`. `LoggerWithContext` injects the HTTP correlation ID under `request_id`, and a collision silently overwrites one with the other (per observability doc §"Request ID glossary").
- [ ] Unit tests in `server/known_for/`: empty scope, no items in category, **items ranked by recency (newest first)** with no completion-bonus reweighting, **10-item cap enforced** (an 11-item input returns exactly the 10 newest), items across multiple owners, items in scope-mismatched community correctly excluded, **plus a test that exercises the archived-pivot case** (an experience completed-and-archived must still surface in the detail response and rank purely by its recency timestamp, not by completion). **Both modes covered**: a `ModePerUser` case asserts only the target's items appear and that the member-ID list contains the people they shared with (not the target themselves); a `ModePerCommunity` case asserts items aggregate across owners.
- [ ] **[audit]** Query-budget assertion via `storage.AssertMaxQueries(t, ctx, 7, fn)` matching the chip-derivation ceiling. Tests touching live AI calls (none expected here) would use the `integration` build tag per [CLAUDE.md](../../CLAUDE.md) §"Testing".
- [ ] Service-level test in `server/services/workshop/`: round-trip auth + RPC + proto serialization for both `ModePerUser` and `ModePerCommunity`.
- [ ] **[audit]** Run `npm run build` after the change — covers `gofumpt`, `golangci-lint`, `check-goroutines`, and `check-codeinternal`. Also `go build -tags=integration ./...` per [CLAUDE.md](../../CLAUDE.md) §"Go Server Build Verification" since this adds an exported workshop-service method that integration tests may call.

**Validates:** A pre-existing chip's underlying data is reachable via one RPC call with the same scope rules the chip derivation already enforces — **for both community and user surfaces**.

### Phase 4: Overflow menu — hide or permanently delete a known-for skill

**Goal:** The detail-screen app bar carries an overflow menu (3-dot icon) in the upper right whose actions remove the skill from future surfacing on this user / community. "Hide" suppresses the skill until an explicit unhide; "Permanently delete" suppresses it forever, with a confirmation dialog. After either action the chip derivation (the brief / known-for endpoints) skips this category for the suppressed scope, and the detail screen — if reopened via cache — renders the suppressed empty state from Phase 3.

**Server tasks:**
- [ ] New table `suppressed_known_for` with columns `(scope_kind enum, scope_id text, category_key text, permanent bool, suppressed_by_user_id text, suppressed_at timestamptz, primary key (scope_kind, scope_id, category_key))`. `scope_kind` is `SUPPRESSION_SCOPE_USER` or `SUPPRESSION_SCOPE_COMMUNITY`. Index `(scope_kind, scope_id)` for the chip-derivation lookup. Migration follows the standard storage pattern under `server/storage/`.
- [ ] Storage methods on the existing storage abstraction: `ListSuppressedKnownForByScope(ctx, scopeKind, scopeIDs []string) (map[string]map[string]struct{}, error)` returning `scopeID → set of category_keys`. **[audit]** Batch by scope IDs — never query in a loop (per [CLAUDE.md](../../CLAUDE.md) §"SQL Efficiency" rule 1: N+1 ban). `InsertSuppression(ctx, row)` and `DeleteSuppression(ctx, scopeKind, scopeID, categoryKey)` for the hide / unhide path.
- [ ] Wire the suppression lookup into both **chip derivation** (`known_for.Derive` — drop categories whose `(scope, key)` is suppressed before ranking) and **detail derivation** (`known_for.Detail` from Phase 1 — return `suppressed == true` when the category itself is in the suppression table for the requested scope). ## Follow-up: consolidate polymorphic entity-card messages

The codebase currently carries at least three different "polymorphic
entity card" message shapes that all wrap the same set of underlying
entities (gear / experience / request / giveaway / transfer):

| Message | Lives in | Surface | Discriminator |
|---|---|---|---|
| `AvailableNowItem` | `available_now.proto` | Profile + workshop "Available Now" rails, and (with this issue) the chip detail screen | `AvailableNowKind` enum |
| `BriefCTARow` | `workshop_service.proto` | Workshop "Three ways to keep it going" lean cards | `cta_action` string + `is_primary` |
| `DailyItem` | `portfolio.proto` | Portfolio / inbox daily list | item-type field |

Each was added for a specific surface and diverged in field names
(e.g. `detail` vs `atmosphere_line`) and discriminator type. Real
duplication, but not blocking this issue — consolidating to a single
shared "card" type is a separate refactor with no immediate
user-visible improvement. Tracked at
[#2012](https://github.com/Type2Fun-Foundation/ripls/issues/2012).
