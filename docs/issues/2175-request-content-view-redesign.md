## Problem Statement

The Request content view is the last screen still wearing the pre-#2154 chrome:

- The tab bar shows three tabs (Request / Plan / Chat). The middle **Plan** tab carries impact tiles + the `NeedsSection` only; the Needs row never made it inline onto the first tab the way it did for events.
- The first tab's bottom action block is a `WorkflowActionButtons.buildRequest` morphing pill alongside a `ContentPeopleRow` — a third visual treatment, distinct from the inline row pills and from the rest of the pane.
- Owner management lives in the morphing pill's overflow menu (Edit Details, Confirm Location, Mark Fulfilled, Close Request). Mockup-equivalent: those collapse to a three-item frosted manage sheet opened from a pencil next to the title — exactly the contract `ExperienceManageMenuSheet` ships with today.
- The trailing `AccessRing` widget needs the same swap to `ExperienceAccessPill`-style compact pill that landed for events. (The widget can be lifted from `experience_access_pill.dart` and renamed to a content-view-level primitive; it carries no experience-specific state.)
- The Needs & Contributions sheets still come from `app/lib/presentation/widgets/request/request_needs_sheets.dart` — the legacy editorial chrome. The shared `widgets/needs/` primitives that the Experience scope already consumes (`NeedsProposeSheet`, `NeedsPickerModal`, `NeedsVolunteerSheet`, `NeedsClaimRow`, etc.) have shipped but the Request branch of `NeedsActions` still routes to the old sheets.

The redesign brings the Request screen into row-for-row parity with the Event screen so the two surfaces feel like one product.

## Context from Comments

The issue has no comments yet — I filed it in this session. The issue body and the two parent plan docs (#2154 and #2148) are the spec. Two non-obvious calls already made in the issue body that this plan inherits:

1. **No `RequestResultsPane` in v1.** #2154 kept the Results pane for completed events because `ExperienceResultsPane` already existed and carries content that is genuinely different from the live pane. Requests have no equivalent today — the fulfilled-state impact tiles live inside the Plan pane. Recommendation (carried forward into Open Questions): keep impact rendering off the redesigned first tab for fulfilled requests, render them inline through a new "Impact" row only when `isFulfilled`, and skip building a `RequestResultsPane`. The terminal-state tab bar is `Request + Chat` — two tabs, same as active.
2. **The shared Needs widgets are available.** `app/lib/presentation/widgets/needs/{needs_propose_sheet,needs_picker_modal,needs_volunteer_sheet,needs_claim_row,needs_manage_menu_sheet,needs_archived_sheet,needs_suggestion_grid,needs_volunteer_atoms,needs_sheet_chrome,needs_section,needs_actions}.dart` all exist. `NeedsScope.request(...)` is wired in `app/lib/presentation/viewmodels/needs_scope.dart`. `NeedsActions` is already used by the Request side via `request_chat_pane.dart` for the chat-tab affordance. The remaining work is to (a) push the `NeedsSection` row onto the first tab (the way it sits inline on the Event pane) and (b) cut the import of `request_needs_sheets.dart` from anywhere `NeedsActions` doesn't already drive.

## Potential Solutions

### Option A: One PR, full redesign in place

- **Approach:** Modify `RequestContentView`, `RequestBottomContent`, `RequestRequestPane` in lockstep. Drop the Plan tab, build the inline Needs row, swap the owner avatar for an icon row, replace the bottom action block with an Offer-row built on `ContentInfoRow`, swap `AccessRing` for a shared people-pill, add the edit-pencil + `RequestManageMenuSheet`. Delete `request_plan_pane.dart` and `request_needs_sheets.dart`. Add `state.isTerminal` / `state.chatTabIndex` accessors to `RequestState`.
- **Pros:** Single coherent change matches #2154's structure. No half-shipped intermediate UI. Net code reduction (delete two files: ~717 lines gone, ~250 lines added). Mirrors how the Event side landed.
- **Cons:** Bigger PR — touches ~5 source files plus ARB plus tests. Higher review burden.
- **Effort:** Medium.

### Option B: Phased — chrome first, then Needs migration

- **Approach:** Phase A ships the within-row chrome changes (RSVP-style Offer row, owner icon row, edit pencil + manage sheet, access pill). Phase B drops the Plan tab and folds Needs into a row. Phase C cuts `request_needs_sheets.dart`.
- **Pros:** Each phase reviewable in isolation. The chrome-only phase is low-risk and revertible.
- **Cons:** Phase A leaves a redundant Plan tab side-by-side with the new title-row pencil — two ways to reach the same actions, exactly the confusion the Event-side audit flagged. Phase B leaves `request_needs_sheets.dart` orphan code until phase C.
- **Effort:** Medium-large.

### Option C: Mockup-first prototype, then graft

- **Approach:** Build a parallel `RequestRequestPaneV2` behind a debug toggle, validate on device, then delete the old pane.
- **Pros:** Easy A/B on the same device.
- **Cons:** Codebase memory explicitly bans v2/ suffixed directories (`feedback_theme_reuse.md`). Doubles file count temporarily. Project convention treats parallel rewrites as a smell.
- **Effort:** Large.

## Recommendation

**Option A — single PR, full redesign in place.** Same reasoning as #2154: the mockup is concrete enough to build straight to, the change is mostly cosmetic-with-deletion (no new RPCs, no new state beyond two convenience getters), and Option B's intermediate "Plan tab + title pencil" state is confusing rather than safer. The Event-side template already exists and matches almost line-for-line — porting it to Request is mechanical.

The pieces worth confirming with the user before opening the PR:

1. Whether fulfilled requests render an inline "Impact" row on the first tab, or whether impact gets dropped from the post-fulfillment UI entirely. The current Plan pane shows `ContentImpactTiles` + `QtAttributesCard` — those are real product features, not chrome.
2. Whether "Edit Details" opens the existing inline edit-mode flow (`onToggleEditMode`) or a new dedicated sheet. Recommend mirroring #2154 — reuse inline edit mode.
3. What non-owner offer affordance the new Offer row exposes. The existing `WorkflowActionButtons.buildRequest` produces a coral CTA ("Offer to help") that morphs sage on offered. The trailing pill on the new Offer row should carry that same toggleable CTA — `_RowCallToActionPill` from the Event side fits the shape exactly.

Both recommendations are stated in Open Questions.

## Open Questions

- **Where do post-fulfillment impact tiles + the quality-time attributes card render?** — Recommendation: **Inline on the first tab as a new "Impact" row that expands inline when tapped, only present when `request.state == REQUEST_STATE_FULFILLED`.** The `ContentImpactTiles` widget is roughly card-shaped, so the path of least change is to fold it as a sixth row (or as collapsible content rendered between the description and the row stack). If the row treatment is too cramped for the tile grid, fall back to keeping `ContentImpactTiles` as a section below the rows, gated on `isFulfilled`. Either way the **Plan tab is dropped** — impact moves onto tab 0. `QtAttributesCard` becomes editable inline by owners only, which matches its current behavior.
- **Does "Edit Details" open inline edit mode or a dedicated sheet?** — Recommendation: **Inline edit mode** via the existing `onToggleEditMode` callback. This matches #2154 and avoids forking the title/description/cover-photo edit surface. Source-URL editing isn't applicable to Request (the pane doesn't expose one today); the inline edit-mode flow already covers title + description + cover-photo replacement.
- **Three-item or four-item manage menu?** — Recommendation: **Three items by default — Edit Details, Mark Fulfilled, Close Request — and one extra item (View Impact) when `isFulfilled`.** Reuses the existing `requestMenuViewImpact` ARB key. Mirrors how #2154 handles the same case for completed events. The current overflow's `requestMenuConfirmLocation` is dropped because the location row already exposes the picker on tap.
- **What replaces the bottom action block for non-owners?** — Recommendation: **An Offer row built on `ContentInfoRow`.** Leading icon `Icons.volunteer_activism_outlined`, value built through `valueBuilder` (an offerer avatar stack lifted from the existing `ContentPeopleRow` + a "{N} helping" summary), trailing pill is the existing offer/withdraw CTA. Tapping the row opens `HelperListSheet`. For owners, the same row replaces the bottom block; the trailing pill becomes a "Managing" sage chip when the owner has at least one offerer, mirroring the way the morphing pill toggles state today. The row is **always present** (even on a terminal fulfilled/cancelled request, where the trailing pill is dropped but the offerer summary remains for context, exactly like the RSVP row on the Event side).
- **`AccessRing` replacement — promote `ExperienceAccessPill` to a shared content-view widget?** — Recommendation: **Yes, rename and move it.** The widget has no experience-specific state — it just shows a glassy people-count pill. Lift it to `app/lib/presentation/widgets/content/content_access_pill.dart` (or `access_pill.dart`), keep the `experienceInvitesPill` ARB key (or rename to `contentAccessPill`), and have both screens import it. The Experience side then drops its widget. If a rename is too much churn for this PR, keep the widget in place and have the Request screen import it directly from the experience directory; flag a follow-up to relocate.
- **Tab-bar collapse for terminal requests — preserve a Results tab?** — Recommendation: **No.** Unlike #2154 which kept `ExperienceResultsPane` for completed events, Requests have no equivalent pane today and the existing impact-tile content fits cleanly inline. Two tabs (Request + Chat) for both active and terminal requests. This keeps the tab math simple — `chatTabIndex` is always `1` for the Request side.
- **Should `state.isCompleted` / `state.chatTabIndex` be added to `RequestState` for symmetry with `ExperienceState`?** — Recommendation: **Add `state.isTerminal` and `state.chatTabIndex` getters to `RequestState`.** Replace the hardcoded `activeTab == 2` checks in `request_content_view.dart:133`, `request_bottom_content.dart:60`, and `request_chat_pane.dart:68` with the named accessor. Even though `chatTabIndex` is always `1` after the redesign, the named getter is clearer at the call site and keeps the symmetry with the Event side. `isTerminal` already has consumers (see `request_plan_pane.dart:37`, `request_request_pane.dart:219`) that re-derive it locally; centralize it.
- **`state.isOwner` already exists**, no change needed there.
- **Where does the Needs row sit in the row stack?** — Recommendation: **Below Location, above Offer.** Three rows total in the read view: Location, Needs, Offer. Owner-row → swap to icon row, position before description? On the Event side the owner row is folded into a fifth icon-leading row at the bottom of the stack; on the Request side the equivalent is the Offer row (which is also "people-oriented"), so the owner row can sit between description and Location, or be dropped entirely (the requester's name is already on the access pill / shows in the AccessSheet). Recommendation: **drop the standalone owner row** to keep the stack to three rows. If we keep it, place it last and swap `ContentAvatar` → `Icons.person_outline`. Decide at implementation time once the stack lays out on a real device.
- **Row pill completed-state restyling.** Same as #2154 — the trailing CTA pill renders a translucent sage chip (`AppColors.experienceSageGreen.withValues(alpha: 0.22)` fill, `0.35` border) when the user has offered. Reuse `_RowCallToActionPill` (or whatever the Event side ended up calling it after the #2154 implementation) rather than minting a Request-specific version.
