## Problem Statement

#2702 taught a **request** to morph into a real loan/giveaway: a helper claims a gear-backed need, the claim escalates into a child transfer (`Transfer.origin_request_id`, born `RECIPIENT_SELECTED`, requester = recipient), and the two lifecycles drive each other over the community-event bus. This issue extends the same machinery to the **experience** scope: a participant who claims a "wheelbarrow" need on a yard-day event should be able to lend their actual wheelbarrow *for the event* — a child transfer of the experience that mirrors the request flow, giving a real loan record and item-based impact instead of today's display-only gear link.

The planning layer (needs & contributions) is already shared by both scopes, and experience-scoped contributions already carry an optional `gear_id`. What is missing is the escalation: an experience contribution never becomes a `Transfer`, there is no `origin_experience_id`, and no lifecycle coupling exists.

The load-bearing difference from #2702 is that **an experience has no unambiguous asker**. A request is owned by one person (the requester) who is the obvious recipient; an event has a host plus N attendees, gear typically changes hands *at* the event, and the item usually goes home with the lender afterward. So the recipient, the handoff/return lifecycle, and the coupling direction all need event-native answers — resolved in **Design Decisions** below.

### Codebase reality (verified 2026-07-12)

- **Transfers are request-scoped only.** `Transfer.origin` is a oneof with a single member `origin_request_id = 19` (`proto/ripls/models/transfer.proto:56-58`); no `origin_experience_id`. Next free field in the message is **21** (`origin_request_id`=19, `deleted`=20).
- **`OfferTransfer` hard-codes request assumptions** (`server/services/transfer/offer.go`): recipient must equal `request.RequesterId` (`:116`), caller ≠ requester (`:119`), request state `ACTIVE`/`OFFERS_RECEIVED` (`:122`), shared via a non-archived `CommunityRequest` (`:126`). Message shape: `OfferTransferRequest` in `proto/ripls/api/transfer_service.proto:256-281`.
- **Experience contributions carry gear but never escalate.** `ClaimExperienceNeed` (`server/services/experience/needs.go:272-366`) validates an optional `gear_id` via `planning.ValidateGearLink`, decrements the slot, inserts a `PlanningContribution` with `Scope = ExperienceId` — and never sets `TransferId`. There is **no `ensureRequestOffer` analog** and no auto-RSVP on the *server* (the client submits the YES RSVP first; Intentional difference #1 in `client/needs.md`).
- **The back-ref fields are already scope-agnostic.** `PlanningContribution.transfer_id` (`planning.proto:62`) and `accepted_at_unix_sec` (`planning.proto:67`) exist and are usable from the experience scope today — just never written there. But `planning.ValidateTransferLink` (`server/planning/link_transfer.go:17-45`) hard-codes `contribution.GetRequestId() != requestID` (`:27`) — it needs a scope-aware variant.
- **Experience lifecycle transitions are inline in the RPC handlers** (`server/services/experience/lifecycle.go`), not a state machine. Completion (`CompleteExperience`, `:120-402`) is owner-only, sets `CompletedAtUnixSec`, auto-marks attendance, and emits `COMMUNITY_EVENT_TYPE_EXPERIENCE_COMPLETED` (29) per shared community; cancel emits `_EXPERIENCE_CANCELLED` (39); start emits `_EXPERIENCE_STARTED` (38). The `CommunityEvent.Topic` oneof already supports `ExperienceId`.
- **Loan state machine forbids the transition Bryan chose.** `isValidTransition` (`server/services/transfer/state_machine.go:287-294`) allows `RECIPIENT_SELECTED → COMPLETED` **only for giveaways**; a loan must pass through `ACTIVE`. `expected_return_unix_sec` (and therefore the return reminder) is computed **only on the `ACTIVE` transition** (`state_machine.go:103-109`; reminder reconciler `server/jobs/scheduled_notifications/loan_return_reminders.go`). So skipping `ACTIVE` naturally means no return reminder and no gear-state flip — exactly the event-native behavior.
- **The bus-subscriber pattern is established.** `server/services/request/transfer_subscriber.go` (request reacts to transfer events) and `server/services/transfer/request_subscriber.go` (transfer reacts to request events) both implement `cebus.Subscriber` (`Name()` + `Handle()`), registered in `server/wiring.go:386-393`. The `gearSharer` hook is injected at `wiring.go:380`.
- **API assembly analog exists.** `buildRequest` (`server/services/request/helpers.go`) enriches the supply side via `buildRequestGearOffers` (`:233-303`, batch fetch of transfer/gear/helper) onto `Request.gear_offers`. The experience analog is `buildAPIExperiences` (`server/services/experience/build_api.go:23`); the natural surface for the event is the **contribution row**, not a separate array — `ExperienceContributionResponse` (`proto/ripls/api/experience.proto:36-49`) exposes `gear_id` but no `transfer_id`/`transfer_state`.
- **Impact is orthogonal, not adopted.** `BuildExperienceImpactMetrics(valueUSD, attendeeCount, …)` (`server/impact_metrics/builder.go:159`) derives the event's money/emissions from the event's own `value_estimate` and time from attendee count. The request's #2702 adoption/masking (`impact_metrics.MaskTransferAdoptedRequestDimensions`) exists because a request's projected value would double-count the transfer; an event's value is its own materials, so the child transfer's item impact is additive (see Open Questions Q2).

## Design Decisions (from the design interview, 2026-07-12)

1. **Recipient = the event host (owner).** The child transfer is `owner_id = lender (participant)`, `recipient_id = experience.owner_id`. This is the closest analog to #2702's "requester = recipient": the host is the event's representative, and the loan is "to the host for the event's duration." **Guard: lender ≠ host** (mirrors `OfferTransfer`'s caller ≠ requester). A self-loan is meaningless, so a host bringing their own gear does not escalate (decision 3).

2. **Lifecycle: event-driven, skip the manual handoff.** The transfer is born `RECIPIENT_SELECTED` at claim time; it **auto-COMPLETEs on `EXPERIENCE_COMPLETED`** (loan and giveaway alike) and **auto-CANCELs on `EXPERIENCE_CANCELLED`**. There is no `ACTIVE` hop and no return reminder — the lender takes their own item home, so a return reminder would be nonsensical, and skipping `ACTIVE` is what suppresses it structurally (the reminder is derived from the `ACTIVE`-only `expected_return_unix_sec`). `loan_duration_days` / the return date on the record are **derived from the event's end time** for display honesty. The coupling is **one-directional** (experience → transfer): a gear handoff never changes experience state — the host completes the event by their own action, unlike a request that auto-fulfills.

3. **Host self-contributions stay display-only in v1.** A host bringing their own gear to their own event does not escalate (self-loan has no counterparty). Item-based impact for host self-contributions is a follow-up. Non-host participants' gear contributions escalate; host contributions render as today's plain gear link.

## Potential Solutions

The interview converged on the *semantics* (Design Decisions 1–3). The remaining open architectural fork is the **RPC surface** for creating the experience child transfer. Options recorded for the audit trail:

### Option A: New `OfferExperienceTransfer` RPC (CHOSEN)
- **Approach:** A dedicated RPC parallel to `OfferTransfer`, with its own `OfferExperienceTransferRequest/Response` messages, handled in `server/services/transfer/offer_experience.go`. The shared tail (gear ownership/availability validation, community share via `gearSharer`, transfer insert, contribution back-ref via `server/planning`, conversation add, community event) is factored into a helper reused by both `offer.go` and `offer_experience.go`. Recipient is resolved server-side to `experience.owner_id` (not taken from the client). Experience-scope validation: experience is `ACTIVE`/`JOINED`/`IN_PROCESS`, shared into `community_id` via a non-archived `CommunityExperience`, caller is a participant, caller ≠ owner.
- **Pros:** Each RPC's contract evolves independently (proto convention: no cross-RPC message reuse); the divergent validation (recipient = host, experience state, `CommunityExperience` share) stays readable; the request path is untouched; server owns recipient resolution (client can't target an arbitrary user).
- **Cons:** Some duplication between the two handlers (mitigated by the shared helper); a second RPC to test and document.
- **Effort:** Medium.

### Option B: Extend `OfferTransfer` with `origin_experience_id`
- **Approach:** Add an `origin_experience_id` field (mutually exclusive with `origin_request_id`) to `OfferTransferRequest` and branch the handler on which origin is set.
- **Pros:** One RPC, one client method; the shared tail isn't duplicated at the handler level.
- **Cons:** A fat handler mixing two recipient models, two state-validation paths, and two share-check tables; the request contract stops evolving independently; the client must send a recipient the server should actually derive. Rejected.
- **Effort:** Medium, worse ergonomics.

### Option C: Generalize `OfferTransfer` around an `origin` oneof in the request message
- **Approach:** Replace the flat `origin_request_id` with an `origin { request_id | experience_id }` oneof on `OfferTransferRequest` and a strategy object per scope.
- **Pros:** Symmetric; one RPC that scales to future origins (chat, portfolio).
- **Cons:** Breaking change to a shipped RPC message; premature abstraction for two scopes (over-engineering — see the minimal-dependencies principle); the recipient/state divergence still has to live somewhere. Rejected for v1; revisit if a third origin appears (#2266).
- **Effort:** Large.

## Recommendation

**Option A**, with Design Decisions 1–3. The architecture-sensitive points, all consistent with `server/architecture.md` § Service Independence:

- **Coupling runs one-directional over the bus.** A new **experience-lifecycle subscriber in the transfer service** (`server/services/transfer/experience_subscriber.go`, registered in `wiring.go`) consumes `EXPERIENCE_COMPLETED` → complete non-terminal `origin_experience_id` transfers, and `EXPERIENCE_CANCELLED` → cancel them. The experience service reads nothing from the transfer service and vice-versa; each mutates only its own aggregate. No reverse subscriber is needed — events don't auto-complete from a handoff (decision 2), which makes this strictly simpler than #2702's bidirectional coupling.
- **The `RECIPIENT_SELECTED → COMPLETED` loan transition is opened narrowly.** `isValidTransition` gains a case allowing that jump for **loan transfers carrying `origin_experience_id`** (giveaways already skip `ACTIVE`). Because `ACTIVE` is skipped, `expected_return_unix_sec` is never set, so no reminder is scheduled and the gear never flips to `UNAVAILABLE` — the correct behavior for a communal item the owner keeps.
- **Claim + escalation stays client-orchestrated in two RPCs** (claim → `OfferExperienceTransfer`), exactly like #2702. If call 2 fails, the degraded state is today's display-only gear link, and the claim can be re-confirmed to retry.
- **Recipient is derived server-side.** Unlike `OfferTransfer` (which takes `recipient_user_id` and validates it equals the requester), `OfferExperienceTransfer` reads `experience.owner_id` — the client never names the recipient, closing an authorization hole.

## Open Questions

Two of the interview's secondary refinements were **left unresolved** (Bryan selected only "host self-gear stays display-only"); both carry a recommendation to confirm during implementation. Plus minor implementation-time questions.

- **Q1 — Does completion gate on attendance?** At `EXPERIENCE_COMPLETED`, should the subscriber complete child transfers only for contributors marked `ATTENDED_STATUS_YES` (cancelling no-shows, who never brought their gear), or complete **all** non-terminal origin-experience transfers? — **Recommendation: complete all non-terminal transfers regardless of attendance in v1.** Attendance recording is optional and frequently skipped (`autoMarkAttendanceIfNeeded` marks all YES intentions attended anyway); gating adds a data dependency for a marginal correctness gain. Revisit if hosts report "ghost loans" from no-shows — the refinement is a one-line filter on the roster.
- **Q2 — Does the event child transfer's impact need masking?** #2702 masks the request's own money/emissions because they'd double-count the transfer. An event's `value_estimate` is its own materials (food, supplies), conceptually disjoint from a borrowed wheelbarrow. — **Recommendation: additive, no masking** — the event keeps its time/value impact, the child transfer's money+emissions count once on the transfer. **Verify** during Phase 2 that no code path folds a contribution's gear value into `Experience.value_estimate`; if one does, apply the #2702 masking pattern. Add an explicit impact-double-count test.
- **Q3 — Is there a host "accept" affordance?** #2702 gives the requester an optional "this one works" (`AcceptRequestOffer` → `accepted_at_unix_sec`). — **Recommendation: no accept in v1 for experiences.** The claim itself is the commitment and completion drives everything; a host accepting each brought item is ceremony the event context doesn't need. `accepted_at_unix_sec` stays unset on experience contributions. Record under **Intentional differences** so it isn't flagged as drift; revisit if hosts want to curate.
- **Q4 — Giveaway-to-host semantics.** "Give" on an event claim means giving to the host (e.g., donate a tool to the community-garden shed — host stewards it). This is coherent for the communal-steward case but wrong for a swap-meet/free-pile where the item goes to an arbitrary taker. — **Recommendation: support giveaway-to-host mechanically (host = recipient), scope true multi-recipient event giveaways out of v1** and note the limitation; a swap-meet primitive is a separate issue.
- **Q5 — Duration derivation for TBD/undated events.** `ExperienceTime` may be `TimeTBD` or unset (no date). — **Recommendation:** derive `loan_duration_days` from the event end (`SpecificTime.start + duration_minutes`, or `TimeRange.end_unix_sec`) rounded up to whole days; when the event is undated, **leave `loan_duration_days` unset** — since `ACTIVE` is skipped the field is cosmetic for the record anyway.
- **Q6 — Undo of event completion vs. completed child transfers.** `CompleteExperience` is undoable (`UndoData_ExperienceCompletion`, `lifecycle.go:331-344`). If auto-completing the event completed the child transfers, does undoing the completion revive them? — **Recommendation: no — completed child transfers stay completed in v1** (mirrors #2702's "terminal transfer states don't revive"; re-escalating on re-completion is cheap). Document as a known asymmetry in `workflows/experience.md`. Verify the undo path (whatever consumes `EXPERIENCE_COMPLETED`'s undo) doesn't error on the now-completed transfers; if hosts hit real "undid the event, loan still shows completed" confusion, revisit with an explicit revive step.

## Audit notes (2026-07-13)

Applied during the `/ripls-audit` pass; each item names the standard it enforces.

1. **Service independence made explicit** (`server/architecture.md` §1): the offer handler and the lifecycle subscriber read `Experience` / `CommunityExperience` / the child transfers via shared `storage`, **never** by calling the experience service — stated in both Phase 1 and Phase 2. Mirrors #2702 audit item 9.
2. **Authorization tightened** (security review §4 — authorization bypass / IDOR): recipient is derived server-side from `experience.owner_id` (client never names it); the escalated contribution must **belong to the caller** (userID-scoped `ValidateTransferLink`), not just to the experience. Added the "someone else's contribution" rejection to the Phase 1 test matrix.
3. **Item-based impact at completion, not creation** (corrected during implementation — the request `OfferTransfer` leaves `impact_estimate` unset at offer time; the completion transition computes it via `BuildTransferImpactMetrics`).
