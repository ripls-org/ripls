# Server Localization (l10n)

> Status: Phases 0–3 shipped (issue #1904); the in-app
> structured-template migration shipped as #2827. Push notifications
> and user-facing emails render in the recipient's locale; in-app
> surfaces render client-side from typed fields, with the deprecated
> server copy fields retired by #2835. #2936 removed AI-authored prose,
> which was the last category of user-visible string outside a catalog.

The ripls server emits user-visible strings on five surfaces:

1. Push notifications (FCM/APNs payloads pre-rendered by the server)
2. Email (subjects, headers, HTML/text bodies sent to Mailgun)
3. SMS (off-app notification copy and host-relayed invites)
4. SSR web landing pages — the `/go/{code}` invite/event/gear/request
   pages the web service server-renders for link previews and the
   phone-first pre-auth flow (#2090). These resolve locale purely from
   the visitor's `Accept-Language` (a pre-auth page has no stored
   preference); the `/go/` route is wrapped in
   `middleware.AcceptLanguage`.
5. In-app text the user reads inside the Flutter app (stories, system
   chat messages, RPC error strings)

This document defines how those surfaces become localized.

## The render boundary

> The **client** renders any string the user reads inside the app.
> The **server** renders only strings where the server is the
> terminal emitter — push notifications, emails, SMS.

The two l10n systems do not share keys. Their message sets are
disjoint (push/email copy on the server; UI labels and in-app
templates on the client), so they do not need a shared catalog format
or a build-step converter. The server holds its own catalog under
`server/l10n/source/`; the client holds the ARB catalog under
`app/lib/l10n/`.

This boundary exists to avoid parallel-catalog drift. Two catalogs
covering the same in-app screens would diverge in terminology and
voice the moment translators touched one side without the other.

### Why not a single shared catalog?

go-i18n's TOML/JSON format and ARB have different shapes (ICU plural
syntax differs, metadata blocks differ). Mapping between them costs
real tooling. The disjoint message sets do not justify the cost: a
push notification key (`notif.community_event.transfer_active.title`)
never appears in the client; an in-app label
(`gearDetailScreenTitle`) never appears in a notification. ARB-as-
shared-source is **not** adopted.

### The boundary has no exceptions

It used to have one. Free-form AI-authored prose — nudge cards, story
copy, Workshop hero copy, impact narratives — was rendered by the
server with the locale wired through to the prompt (Phase 5 of
#1904), and sat in no catalog on either side. The model authored
directly in the recipient's language.

#2936 removed that prose, and with it the exception. Every in-app
string now resolves from a catalog: the client's ARB for UI labels and
structured templates, the server's TOML for push, email, and SMS.

The exception was also a quiet localization hole. A generated string
is persisted as one literal in whatever language it was written in,
so a story or nudge produced for an English-speaking user stayed
English for every later reader regardless of their locale — and
nothing flagged it, because there was no key to be missing. Rendering
from `template_key` + params fixed that as a side effect: the same
story resolves per viewer.

## Locale identity and resolution

`models.User.preferred_language` (field 19) holds the user's BCP-47
language tag (`en`, `es`). Seeded from the `Accept-Language` header
of the registration request; defaults to `"en"` when absent.

Every authenticated RPC carries an `Accept-Language` header set by
the client from the user's `localePreferenceProvider`. The server
prefers it over the stored `preferred_language` so a user who
switches locale sees translated content immediately, before the
next profile-update RPC lands.

`l10n.LocaleFromContext(ctx)` resolves the locale with this priority:

1. Explicit RPC argument (rare — handlers that take a locale param)
2. `Accept-Language` request header
3. The authenticated user's stored `preferred_language`
4. `"en"`

The resolver returns a normalized tag. `Normalize` lower-cases,
strips region subtags, and falls back to `"en"` for unsupported
tags.

### Email locale resolution

Email locale resolution **inverts** the general RPC priority: the
recipient's stored `preferred_language` wins over the request's
`Accept-Language`. The email is read by the recipient, who may not
be the requester (password reset triggered from a different device
than the one where they configured their locale), and the stored
preference represents their deliberate choice. The helper
`localeForRecipient(ctx, recipientPreferred)` in
`server/email/locale.go` encodes this:

1. `recipientPreferred` (the User's stored `preferred_language`)
   when non-empty.
2. `l10n.LocaleFromContext(ctx)` — folds any RPC-supplied locale
   and the request's `Accept-Language`. For flows with no
   recipient User row (waitlist welcome) this is the only signal.
3. `l10n.DefaultTag` (English).

**Detached-goroutine ctx propagation.** Callers that background the
send (e.g. `JoinWaitlist` spawns the welcome email in a goroutine
with `context.Background()`) must capture the request locale up-front
and re-inject via `l10n.WithLocale(emailCtx, tag.String())`. Without
this, every backgrounded email would render in the default locale.
`server/services/waitlist/service.go::JoinWaitlist` is the reference
pattern.

**Admin emails are English-only.** The activity digest
(`server/jobs/activity_digest{,_weekly}.go`) and the waitlist
notification (`SendWaitlistNotification`) go to a single configured
staff recipient, not to end users — both are intentionally not
localized. Adding new admin-recipient emails should follow the same
pattern: render in English, document the recipient model.

### Email body templates

Per-locale template files live next to the Go code:
`server/email/{flow}_template_{locale}.{html,txt}` (e.g.
`password_reset_template_es.html`). The send path picks the right
pair via `localizedTemplates.pick(tag)` and falls back to the
English file when a locale is missing. This avoids mixing go-i18n
placeholders inside Go `html/template` syntax (both use `{{...}}`)
and lets translators edit a self-contained file. Per-flow templates
(password reset, waitlist welcome) flow only their **subject** through
the TOML catalog as `email.<flow>.subject` and bake the body into the
per-locale template files. Off-app emails that reuse the shared
`notification_template_{locale}` shell instead render both subject and
body from the catalog (e.g. `email.invite.subject` + `email.invite.body`).

## Server catalog

`server/l10n/source/{en,es}.toml`. Source files are committed to the
repository and embedded into the binary via `go:embed`. go-i18n v2
(`github.com/nicksnyder/go-i18n/v2`) is the rendering library.

### Catalog scope

The server catalog contains push notification copy, off-app
notification copy (the SMS/email `message` + `cta` strings and the
`sms.brand_prefix`/`sms.optout` framing), email subjects, the
localizable text inside email templates, and the SSR web-landing copy
(the `web.*` and `common.*` keys the `server/services/web` templates
render — CTAs, error states, OG/title copy, and the localized
weekday/month names the event landing assembles because Go's
`time.Format` is not locale-aware). It does **not**
contain story prose, chat system messages, or in-app RPC error text
— those live in the client ARB and are emitted by the server as
`{template_key, params}` payloads.

### Key naming convention

- Push notifications: `notif.<event_family>.<event_kind>.title`,
  `notif.<event_family>.<event_kind>.body` (e.g.
  `notif.community_event.transfer_interest_expressed.title`).
- Email: `email.<flow>.subject`, then in-template strings keyed by
  semantic role (`email.digest.section_engagement` etc.).
- Off-app (SMS/email) notification copy: `notif.offapp.<kind>.message`
  and `notif.offapp.<kind>.cta`, plus the SMS framing strings
  `sms.brand_prefix` and `sms.optout` (rendered by
  `server/notifications/notification_content`).
- Notification stand-ins: `notif.standin.<entity>` (`actor`, `gear`,
  `experience`, `request`, `community`, `planning_item`) — the
  localized generic noun substituted when a notification template
  param resolves to an empty name, so a missing lookup never renders
  a blank slot in push/SMS/email copy.
- SSR web landings: `web.<page>.<role>` (`web.event.cta_in`,
  `web.gear.headline.giveaway`, `web.invite.youre_invited`,
  `web.error.<kind>`, `web.capacity.*`, `web.when.*`), rendered by
  `server/services/web`. Shared chrome uses `web.common.*`.
- Generic fallback strings used across surfaces: `common.<name>`.

Keys are lowercase, dot-separated, ASCII. They are not human-facing —
translators read TOML messages, not keys.

### Catalog file format

```toml
[notif.community_event.transfer_interest_expressed.title]
other = "Interest in {{.GearName}}"

[notif.community_event.transfer_interest_expressed.body]
other = "{{.ActorName}} wants to borrow your {{.GearName}}"
```

`other` is the default plural form for messages without explicit
plural rules. Use `one`/`other` keys for plural-bearing strings;
go-i18n applies CLDR plural rules per locale.

### Source format choice

TOML is the chosen format for new server catalog files. go-i18n v2
supports TOML/JSON/YAML; TOML is the most readable for translators
handling dozens of short push/email strings with optional ICU
plural rules.

## Adding a new server-rendered string

1. Add a key to `server/l10n/source/en.toml` (English source of
   truth).
2. Add the same key to every other locale source file
   (`server/l10n/source/es.toml`). `npm run lint:go:l10n-parity`
   fails CI on missing keys.
3. In code, render via `Localizer.T(key, params)` instead of
   `fmt.Sprintf`. The new string must never appear inline in the
   files listed in `scripts/check_no_inline_user_strings.js`
   (`SCANNED_FILES`), where
   `npm run lint:go:no-inline-user-strings` blocks regressions.
4. When adding a wholly new user-facing surface (a new email
   template, a new notification subscriber), extend
   `scripts/check_no_inline_user_strings.js::SCANNED_FILES` to
   cover the new file so the guard catches future regressions.

## Adding a new in-app server-emitted string

In-app strings — stories, system chat messages, RPC view copy,
user-visible RPC errors — are never in the server catalog and are never
rendered by the server. The server emits *structure*; the client renders
copy from its ARB catalog at widget build time (#2827 is the migration
that closed the historical exceptions; #2835 removed the deprecated copy
fields it had left populated for released builds). Three mechanisms,
by surface:

1. **Chat system messages** — emit `{template_key, template_params}`
   via a `chat.LocalizedMessage` helper
   (`server/chat/system_message_templates.go`). Params are verbatim
   user content or machine-readable values (a Unix timestamp plus UTC
   offset, never a pre-formatted date); the client's
   `system_message_text_resolver.dart` maps the key to an ARB entry.
   A state with no value (an unset time, an unnamed location) gets its
   own template-key variant, not an English placeholder param.
2. **RPC view copy** (Home decisions, calendar entries, impact
   breakdowns) — model the semantic as a typed proto field: an enum
   (`HomeDecisionReason`, `HomeUpNextStatus`, `ImpactSourceType`), a
   raw timestamp or number the client formats in the viewer's locale,
   and optional string fields carrying only verbatim user content
   (absence means "render a localized fallback"). The client resolves
   copy in a shared per-surface resolver (`home_decision_copy.dart`,
   `home_up_next_copy.dart`, `impact_copy.dart`).
3. **User-visible RPC errors** — the stable-code path below.

In every case: add the key to `app/lib/l10n/app_en.arb` **and**
`app_es.arb` (parity is CI-gated), and render via `context.l10n.<key>`
in widget `build()`. `scripts/check_no_inline_user_strings.js` carries a
strict `NO_COPY_FILES` mode for migrated in-app surfaces — a file
enrolls once its last English literal is gone. #2835 enrolled the
portfolio home-view and impact metric-detail surfaces once their
deprecated copy fields came off the wire, and #2844 finished the
experience chat params.

**A stand-in for a value the server could not resolve belongs to the
client too.** An unresolved person's name travels as an empty
`actorName` param and the client substitutes its own
`serverChatSystemUnknownPerson`; a concrete time travels as
`timeUnixSec` + `timeUtcOffsetMin` and the client formats it. The
server's English `description` column keeps its own stand-ins (via
`chat.actorOrSomeone` / `TimeParam.englishTime`) because that column is
the pre-Phase-4b fallback and is deliberately English — but nothing it
renders may leak into `template_params`, which is where #2844's
violation lived. Verbatim user content — an organizer's own free-text
time, an item's name — is the exception: it passes through as-is,
untranslated, and gets no stand-in.

For user-visible RPC errors, the server returns a stable code +
params via `connect.Error` details; the client maps to an
`rpcError*` ARB key through the existing `RpcErrorHandler` pair
(see `app/lib/core/errors/README.md`).

### User-visible RPC errors (Phase 4a)

The mechanism is live for new error sites:

1. Define a stable, snake_case code (e.g. `experience_owner_required_for_delete`).
2. Server returns the error via `connecterr.UserVisible(ctx, connectCode, code, fallbackEnglishMessage, params)`. The fallback message is still on the wire so older clients without the detail-handling code show readable text.
3. Add a paired ARB key (`rpcError<UpperCamelCase>`) to `app_en.arb` and `app_es.arb`.
4. Add a case to `_localizeServerCode` in `app/lib/core/errors/rpc_error_handler.dart` mapping the code → ARB getter.

The client's `RpcErrorHandler.classify` walks the Connect error's details, surfaces a `LocalizedErrorDetail` as `UserError.localizedCode(code, params)`, and falls back to per-Connect-Code rendering if no detail is present. Unknown codes (server newer than client) render `rpcErrorGeneric` instead of crashing.

Codes are an append-only contract: never rename or repurpose; add a new code for the new semantic.

## Runtime behavior

Missing translations are not fatal. The localizer renders the English
fallback and logs a rate-limited `Warn` via
`logging.LoggerWithContext(ctx)` with the requested locale, the
missing key, and the calling operation. The rate limit (`sync.Map`
seen-set) ensures each missing key logs at most once per process
restart — missing translations are expected steady-state during
rollout, not alert-worthy.

CI is strict: the parity script asserts every English key has a
translation in every shipped locale source file.
