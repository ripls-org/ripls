# Community Stories System

## Overview

The Ripls Community Stories System automatically generates celebratory content for meaningful community events. When users complete loans, fulfill requests, conclude experiences, or join communities, the system creates stories that appear in the feed to celebrate accomplishments and reinforce community culture. Stories are ownerless, system-generated feed items that turn individual transactions into shared narratives.

## Architecture Principles

**Template Generation:** Story copy is rendered from a fixed catalog of templates keyed by story type ([templates.go](../server/story/templates.go)). Each result carries a structured `template_key` plus params that the client resolves in the viewer's locale, alongside literal English strings retained for older clients (`TODO(#2159)`).

Stories used to be written by an LLM, with templates as a fallback. #2936 removed that path: the facts a story describes — who, what, when, with whom — are already structured, and narrating them produced copy that read as generated, varied run to run for identical events, and could only ever be English because free prose has no catalog on either side of the [render boundary](server/l10n.md). `TestGenerateFromTemplate_EveryStoryTypeCarriesATemplateKey` guards the invariant that every story type resolves to a key.

**Event-Driven Creation:** Stories are generated by an event-bus subscriber that listens for terminal community events (transfer completed, request fulfilled, experience completed, invitation link used). The emitting services no longer call story generation inline — they publish a `CommunityEvent` to the [community-event bus](../server/community_event_bus/), and [`story_subscriber`](../server/story/subscriber/) does the rest (#510 PR 4). No user action is required.

**Asynchronous Processing:** The bus dispatches to each subscriber on its own goroutine with a bounded ingress channel ([pubsub.MemTopic](../server/pubsub/memtopic.go)), so `Publish` fans out non-blockingly and story creation never blocks the emitting RPC's HTTP response. Each `CreateStory` call is additionally bounded by a 60s `ai.CallWithTimeout` budget inside the subscriber — a generous ceiling left from when generation was an LLM call; template rendering is synchronous and sub-millisecond, so the remaining cost is the storage round trip.

**Library-Based Architecture:** Story content generation is implemented as a standalone library ([server/story/](../server/story/)) rather than a service, following server architecture principles to avoid service-to-service dependencies. The subscriber ([server/story/subscriber/](../server/story/subscriber/)) is a thin event-bus adapter that assembles the story payload and delegates content generation to the library via the `story.Creator` interface.

**Feed Integration:** Stories appear as first-class feed items with type `FEED_ITEM_TYPE_STORY`, displayed alongside gear, requests, and experiences.

**Seamless Transitions:** When experiences conclude or requests are fulfilled, the original feed item is removed and replaced with a celebration story at the top of the feed.

**Multiple Participants:** Stories feature multiple users (not a single owner), celebrating collaborative community activities.

**Deduplication:** Before inserting, `Generator.CreateStory` calls `StoryStorage.Exists(community_id, story_type, related_entity_id)` and skips creation if a matching story already exists. This is an application-level guard (not a DB unique constraint): the check matches the related entity ID against any of the `gear_id` / `loan_id` / `experience_id` / `request_id` columns, scoped to the same `community_id` + `story_type` and excluding soft-deleted rows. If the same event is ever re-handled, the lookup re-runs but does not produce a duplicate — the guard is what lets a future durable, at-least-once transport be dropped in without double-celebrating (see [#510](../docs/issues/510-community-event-pubsub-v2.md) G6).

## Story Generation Flow

### Creation Flow

**Example: Alice and Bob complete a loan of camping gear**

```
Alice returns camping gear → TransferService.CompleteLoan()
    ↓
transitionTransferState() updates transfer state to COMPLETED
    ↓
s.bus.Publish(CommunityEvent{TRANSFER_COMPLETED})   [lifecycle.go]
    ├─ Bus inserts the CommunityEvent storage row (synchronous)
    ├─ Bus pre-fetches denormalized context (Transfer, Gear, Actor)
    └─ Bus fans out non-blockingly to each subscriber goroutine
        ↓  (HTTP response returns here — generation is decoupled)
        story_subscriber.Handle()                   [subscriber/subscriber.go]
            ├─ Skip if community is soft-deleted (community.IsActive)
            └─ Dispatch by event_type → handleTransferCompleted()
                ↓                                    [subscriber/transfer.go]
                Assemble payload from pre-fetched entities:
                    - owner + recipient (or provisional recipient)
                    - participant IDs/names (borrower-first for loans)
                    - media from gear, impact metrics from transfer.ImpactEstimate
                ↓
                ai.CallWithTimeout(60s, creator.CreateStory(req))
                    ↓                                [story/generator.go]
                    Check for existing story (dedup)
                        StoryStorage.Exists(community_id, story_type, transfer.Id)
                        If exists, skip
                    ↓
                    Generate content:
                        generateFromTemplate() — literal English strings
                        PLUS template_key + params so clients render in
                        the viewer's locale
                    ↓
                    Build + insert Story record:
                        story_type, title, description, participant_ids,
                        loan_id/gear_id, media_ids, cost/time/co2 saved,
                        community_event_id (for the Undo link),
                        created_at_unix_sec
                    ↓
                    Log completion (operation: "CreateStory", duration_ms)
    ↓
Story appears in feed on the next fetch (seconds after the action)
```

**Key Architectural Decision:** Story generation is decoupled from the emitting RPC via the community-event bus (#510 PR 4). The four emitter services (transfer, request, experience, community) publish a `CommunityEvent`; the `story_subscriber` listens and calls `story.Creator.CreateStory`. This keeps the emitter RPCs fast and removes the per-service `story.Creator` constructor dependency. See [subscriber/subscriber.go](../server/story/subscriber/subscriber.go), [generator.go](../server/story/generator.go), and the publish site in [transfer/lifecycle.go](../server/services/transfer/lifecycle.go).

### Display Flow

**Example: User views story in feed**

```
User opens feed → FeedScreen loads
    ↓
FeedService.GetFeed() RPC called
    ↓
Server queries feed items including stories
    SELECT * FROM feed_items
    WHERE community_id = "comm123"
    ORDER BY occurred_at DESC
    ↓
Stories included with payload:
    FeedItem {
        id: "story789"
        item_type: FEED_ITEM_TYPE_STORY
        payload: {
            story: StoryPayload {
                story_type: LOAN_COMPLETED
                title: "Adventure Complete!"
                description: "Alice and Bob just completed..."
                participants: [alice, bob]
                media_ids: ["media123"]
                related_loan_id: "loan456"
            }
        }
    }
    ↓
Feed returns to client
    ↓
FeedScreen._buildFeedItem() routes to StoryContentView
    ↓
StoryContentView displays story:
    ├─ MediaBackground with gear image
    ├─ Feed header (system-generated, no actor)
    ├─ Title and description overlay
    ├─ Participant chips (up to 5 users with overflow)
    └─ Related entity navigation
```

**Key Points:**
- Stories come through feed API, no separate story service needed
- Client displays stories using ContentViewBuilders pattern for consistency
- Stories are read-only (no edit mode like gear/requests)
- Participants are clickable to view profiles

## Story Types

### Accomplishment Stories

Generated automatically when community events occur:

All five accomplishment-story types are produced by the `story_subscriber` in response to a published `CommunityEvent`. The emitting service (named below) only publishes the event; the subscriber file named below assembles the payload and calls `CreateStory`.

**STORY_TYPE_LOAN_COMPLETED:** Celebrates successful loan completion with borrower first, then lender. Triggered by the `TRANSFER_COMPLETED` event `TransferService` publishes when a loan transfer reaches the COMPLETED state. See [subscriber/transfer.go](../server/story/subscriber/transfer.go).

**STORY_TYPE_GIVEAWAY_COMPLETED:** Celebrates a completed giveaway with giver first, then recipient. Triggered by the same `TRANSFER_COMPLETED` event for a giveaway transfer; the handler picks the story type from `transfer.TransferType`. See [subscriber/transfer.go](../server/story/subscriber/transfer.go).

**STORY_TYPE_REQUEST_FULFILLED:** Celebrates a fulfilled request with requester and up to two helpers (confirmed helpers preferred, else non-withdrawn offers). Triggered by the `REQUEST_FULFILLED` event published by `MarkRequestFulfilled`; one event (and story) per linked community. See [subscriber/request.go](../server/story/subscriber/request.go).

**STORY_TYPE_NEW_MEMBER_WELCOME:** Welcomes a new community member. Triggered by the `INVITATION_LINK_USED` event published by `AcceptInvitationLink`. This is the only accomplishment story not tied to an undoable action, so it carries no `community_event_id`. See [subscriber/invitation.go](../server/story/subscriber/invitation.go).

**STORY_TYPE_EXPERIENCE_CONCLUDED:** Celebrates a completed experience with its attendees (owner + RSVPs with `attended = YES`, including provisional users by name). Triggered by the `EXPERIENCE_COMPLETED` event published by `CompleteExperience`; one event (and story) per shared community. The handler also formats the editorial kicker and materializes the embedded ESM voting prompt. See [subscriber/experience.go](../server/story/subscriber/experience.go).

## Three-Layer Architecture

### Layer 1: Story Storage

**Purpose:** Persistent story records in database

**Table:** `Story` (Proto-SQL pattern — table name matches the `Story` proto message name verbatim)

**Key Fields:** See [story.proto](../proto/ripls/models/story.proto) for the complete `Story` message. Beyond identity and content, it carries the related-entity IDs used for navigation and dedup (`gear_id`, `loan_id`, `experience_id`, `request_id`), the impact metrics (`cost_saved_usd`, `time_saved_minutes`, `co2_saved_grams`), the optional `community_event_id` that wires the story-screen Undo link, an optional editorial `kicker`, and the structured `template_key` + `template_params` that let new clients re-render the title/description in the viewer's locale (legacy `title`/`description` stay populated as a fallback — see `TODO(#2159)`).

**Deduplication:** `StoryStorage.Exists(community_id, story_type, related_entity_id)` enforces uniqueness at the application layer (no DB unique constraint). It matches the related entity ID against any of the `gear_id` / `loan_id` / `experience_id` / `request_id` columns and ignores soft-deleted rows.

**Storage Operations:** See [story.go](../server/storage/story.go) for Insert, GetByID, ListByCommunity, and Exists methods.

### Layer 2: Story Generation

**Purpose:** Create stories from community events

**Libraries:**
- [server/story/](../server/story/) — content generation. Not a service; avoids service dependencies.
- [server/story/subscriber/](../server/story/subscriber/) — the event-bus adapter (Go package `story_subscriber`) that turns a `CommunityEvent` into a `CreateStoryRequest`.

**Core Components:**
- [types.go](../server/story/types.go) — the `story.Creator` interface and the `CreateStoryRequest` payload struct.
- [generator.go](../server/story/generator.go) — `Generator` struct (implements `Creator`), `NewGenerator(storyStorage)`, and `CreateStory`.
- [templates.go](../server/story/templates.go) — template fallbacks for each story type, emitting both literal strings and a structured `template_key`.
- [subscriber/subscriber.go](../server/story/subscriber/subscriber.go) — `Subscriber` struct, `New(storage, creator)`, and the `Handle` dispatch entry point. Per-type handlers live in `subscriber/{transfer,request,experience,invitation}.go`.
- [generator_test.go](../server/story/generator_test.go) and the per-type `subscriber/*_test.go` files — unit tests.

**Integration:** The emitter services no longer hold a `story.Creator`. Instead, each takes the community-event bus and publishes events; the subscriber is wired separately in `server/wiring.go`. For example, the transfer service constructor is:

```go
func New(storage *storage.ProtoSQLStorage, notificationService notifications.Service,
    bus cebus.Publisher, systemMessageWriter *chat.SystemMessageWriter) *Service
```

and the subscriber is constructed and registered on the same bus:

```go
storyCreator := story.NewGenerator(storyStorage)
storySub := story_subscriber.New(sqlStorage, storyCreator)
communityEventBus.Subscribe(storySub)
```

A `nil` creator means "story generation disabled" — `Subscriber.Handle` returns early.

**No AI dependency:** `Generator` takes no `ai.Provider` — story copy comes entirely from [templates.go](../server/story/templates.go). The `ai` package is still imported for the `ai.StoryType*` discriminators ([story_types.go](../server/ai/story_types.go)), which are plain string constants shared by writers and readers; they live there only to avoid an import cycle.

### Layer 3: Feed Integration

**Purpose:** Display stories in community feed

**Feed Service:** [feed/service.go](../server/services/feed/service.go) includes stories when building feed, converting Story models to FeedItem with StoryPayload.

**Proto Definition:** See [feed_service.proto](../proto/ripls/api/feed_service.proto) for StoryPayload, StoryType, and FEED_ITEM_TYPE_STORY definitions.

**Client Display:** [story_content_view.dart](../app/lib/presentation/screens/story/story_content_view.dart) renders stories using ContentViewBuilders pattern for consistency with gear/request/experience views.

## Architecture Strengths

### ✅ Strengths

1. **Automatic Celebration:** No user action required - accomplishments celebrated automatically
2. **Event-Bus Decoupling:** Generation runs on a subscriber goroutine off the emitting RPC's critical path; emitter services have no `story.Creator` dependency, only the shared community-event bus
3. **Library-Based:** The content generator avoids service-to-service dependencies via the `story.Creator` interface
4. **Deterministic Copy:** Every story renders from a template catalog, so the same event always produces the same words — and those words localize (#2936)
5. **Feed Integration:** Stories appear naturally in feed alongside other content
6. **Seamless Transitions:** Experience/request removal prevents feed clutter
7. **Deduplication:** The application-level `Exists` guard prevents duplicate celebrations
8. **Multiple Participants:** Celebrates collaborative activities appropriately
9. **Proto Consolidation:** Unified StoryPayload reduces API complexity
10. **ContentViewBuilders:** Consistent UI patterns across all content types

## Architecture Considerations

### ⚠️ Trade-offs

1. **Fixed Phrasing:** A template catalog says the same thing every time. That is the point — but it does mean a new story type needs a new template plus its ARB entries, and `generateFromTemplate`'s `default:` arm emits no `template_key`, so a type added without one silently ships English to every viewer. `TestGenerateFromTemplate_EveryStoryTypeCarriesATemplateKey` is the guard.
2. **At-Most-Once Delivery:** The in-process bus drops a dispatch if a subscriber's bounded ingress channel is full (backpressure), and a process crash before the subscriber goroutine runs loses the story — the `CommunityEvent` audit row survives, but the story is not regenerated. A durable transport with at-least-once retry is tracked in [#510](../docs/issues/510-community-event-pubsub-v2.md) (G6).
3. **No User Control:** Users cannot edit or delete system-generated stories (future: privacy preferences)
4. **Fixed Participants:** Participant selection logic is hardcoded per story type (future: configurable rules)

## Future Enhancements

### User Preferences

**Goal:** Allow users to opt-out of being featured in stories

**Approach:** Add `include_in_stories` boolean to user preferences, check before generating stories, either skip story or anonymize participant.

**Benefit:** Respects privacy-conscious users like "Carmen" persona who prefer invisible contributions.

### RSVP Clustering

**Goal:** Prevent feed spam from individual experience RSVPs

**Approach:** Cluster RSVPs within a window and generate a single story ("Sarah, Mike, and 2 others are joining Poker Night") instead of one story per RSVP. The `STORY_TYPE_EXPERIENCE_RSVP = 6` enum value is already reserved in [feed_service.proto](../proto/ripls/api/feed_service.proto) and mapped in the story-type converters, but no subscriber yet produces these stories.

**Benefit:** Reduces feed noise while celebrating community engagement.
