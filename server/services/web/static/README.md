# Server-served static assets

Everything the SSR landing pages (`/go/{code}`, event, gear, request,
community) serve from the binary: `css/`, the self-hosted webfonts in
`fonts/`, `assets/logo.png`, and the two domain-association files under
`.well-known/`. `static.go` embeds them; `Service.staticFS` serves them.

`css/` and `fonts/` are also the marketing site's stylesheets and fonts. The
site reaches them through directory symlinks at `website/content/{css,fonts}`,
which its deploy dereferences (`rsync --copy-dirlinks`) — so there is one copy
of each file, and the server does not depend on the marketing site to build.
`css/gen/tokens.gen.css` is generated by `npm run generate:design-tokens`.

This file lives at the root of `static/` rather than beside the association
files on purpose: `website/content/.well-known` is a symlink, so anything in
that directory is published on the marketing site too.

## Domain association files

`.well-known/apple-app-site-association` and `.well-known/assetlinks.json`
are what let iOS Universal
Links and Android App Links open in the app instead of the browser. The server
embeds them (`server/services/web/static.go`) and serves them at
`/.well-known/` on the deployment's apex domain.

**A fork must replace both.** They name *this* deployment's app identity, and
they are checked against it:

| File | Names | Checked by |
|---|---|---|
| `apple-app-site-association` | `<Apple Team ID>.<bundle id>` | iOS, on install and on link open |
| `assetlinks.json` | package name + SHA-256 signing-certificate fingerprints | Android, via `autoVerify` |

Serving someone else's file is not dangerous, just useless: the OS compares
what it finds here against the app that is actually installed, so an app you
did not sign never associates. The failure is silent — links open in the
browser — which is why this file exists.

Keep the `paths` list in the Apple file in step with the
`android:pathPrefix` entries in `app/android/app/src/main/AndroidManifest.xml`
and the `applinks:` entry in `app/ios/Runner/Runner.entitlements`.

## Why these are checked in rather than parameterized

They are **served to the public internet at a fixed, well-known URL** — every
device that opens one of our links fetches them. There is no confidentiality
to protect, so the tradeoffs that apply elsewhere in #2953 invert: the
identifiers here are already public by construction, in the same class as the
bundle id (plan Correction 8) and the App Links host (Correction 9).

Every alternative costs something real for nothing. Making them runtime config
means `/.well-known/` 404s out of the box and the binary stops being
self-contained; shipping placeholders and overriding at runtime means the
public and private repos carry different content at the same path, which the
export explicitly forbids (Correction 3).

`scripts/oss_scan.js` exempts this directory for that reason.
